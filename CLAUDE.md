# Iteration Room

Unity prototype of a 1-room, first-person time-loop puzzle game (ref: 2016 short film "Iteration 1"). Full design spec: `iteration-game-spec.md`. Layout reference sketch: `iteration_room_layout.png`. `room_layout_sample.png` is an actual film still used as the furniture-placement reference (bed/nightstand/floor-button positions).

**Status**: core loop implemented and manually play-tested as working (hold floor button for a full iteration → next iteration the ghost holds it while the player opens the door). A polish pass (centered furniture, bigger wall grid, real furniture models, shadow-like ghost, jump) has also been applied and rebuilt cleanly. A QA pass (2026-08-09) then found and fixed three defects that a play-test doesn't surface on its own — see **QA findings** below — and an audio/narration layer has been added. A presentation pass (2026-08-10) added the **end-of-cycle collapse** (panel flare + camera shake), replaced the eyelid sweep with a **blink**, decoupled the sit-up, and made the door lamp a **condition readout**; it is built and committed, but **has not been play-tested end to end** — it was verified only by a clean headless build.

The presentation pass has since been play-tested and signed off, and the full SFX set now exists (generated — see **Audio**). A **Room2 puzzle** (drawer → tool → balloons → key → key door) was then added on 2026-08-10 and given one play-test, which raised six items — a physics bug, two polish jobs, a control-teaching problem and a design revert. **All six were implemented and have since been play-tested and signed off** — see **Cleared on 2026-08-10** near the bottom. A **title screen** (`MainMenu.unity` → `PLAY` → async load → `IterationRoom`) and an **Escape pause overlay** were then added, and the prototype was **shipped to itch.io as a WebGL build**.

That first public play-test produced three findings, all since play-tested and committed (`2b34113`): mouse look far too sensitive on the web (a real platform difference, not a tuning miss — see **Mouse sensitivity** for what WebGL actually does to the numbers, and the slider that answers it); the E prompts shown once each and therefore never learned (`ControlHintDisplay` now shows them every time); and **the door button that nobody could find, which has been removed outright** — Room1's door now tracks its floor pad, which is what testers expected and a better teaching moment besides (see `Door`). A fourth, smaller: the end-cycle control's label was wrapping onto two lines, which is likely why testers asked for a skip button that already existed. 
**A third room and an ending** were then added on 2026-08-11. Room3 is four floor pads and a door that needs **all four held at once**, so it takes four past selves overlapping in time rather than one; its walls also carry the game's first diegetic instruction, teaching the end-cycle control on all four sides at once. Walking out of it **ends the run** — the prototype now has a win state, which it never had before, and `LoopManager.RunLoop`'s `while (true)` finally has an exit. Both build clean and their structure is verified in the saved scene, but **neither has been run**: the game is now finishable and nobody has finished it. See **The ending** and **next steps §1**.

**The scene file is no longer tracked in git**: `SceneBuilder` is the source of truth and Unity re-randomises every fileID on rebuild, so run the build to produce it after a fresh clone.

## Stack

- Unity 6000.5.7f1, **Universal Render Pipeline** (`com.unity.render-pipelines.universal` 17.5.0). It started on Built-in deliberately, but the user asked for a realistic look and Built-in with no post-processing was the actual bottleneck — everything reads flat no matter what the materials do. Pipeline assets live in `Assets/Settings/` (`IterationURP` + `IterationRenderer` + `IterationVolume`) and are wired into both `GraphicsSettings.defaultRenderPipeline` and `QualitySettings.renderPipeline`.
  - Materials must use `Universal Render Pipeline/Lit`, **not** `Standard` — URP has no Standard shader, so a material left on it renders magenta. `SceneBuilder.OpaqueShader()` resolves whichever exists, and `SetSmoothness()` handles Standard's `_Glossiness` vs URP's `_Smoothness`.
- Unity MCP: [CoplayDev/unity-mcp](https://github.com/CoplayDev/unity-mcp), registered with Claude Code via `claude mcp add --scope local --transport stdio UnityMCP -- <uvx path> --from "mcpforunityserver==<version>" mcp-for-unity`. **MCP servers only load at session start** — if you're reading this in a session where Unity MCP tools aren't showing up in ToolSearch, that's expected if the session predates registration; the fix is simply to start a new Claude Code session in this directory, not to re-register anything.
- `uv`/`uvx` (installed via winget `astral-sh.uv`) is required for the MCP server to run.

## How this project gets built

There is **no manual scene editing history** — both scenes are assembled by one script, run headlessly. This is the pattern to keep using:

0. **A fresh clone has no scenes** — `Assets/Scenes/*.unity` is git-ignored build output. Run the build below before expecting to open anything. (The `.meta` files *are* tracked; see QA finding 8.)
0b. **There are two scenes, and `MainMenu` is index 0** in `EditorBuildSettings`, so that is where a standalone player opens. `IterationRoom` is index 1 and is what `MainMenu` loads. Pressing Play in the Editor runs whichever is open, which is convenient: open `IterationRoom` to iterate on the game, open `MainMenu` to test the title screen.
1. Edit C# under `Assets/Scripts/` and/or `Assets/Editor/SceneBuilder.cs`.
2. Rebuild headlessly:
   ```
   "C:\Program Files\Unity\Hub\Editor\6000.5.7f1\Editor\Unity.exe" -batchmode -nographics -projectPath "C:\Users\seonl\Desktop\c\2026\summer\Iteration" -executeMethod IterationRoom.EditorTools.SceneBuilder.Build -quit -logFile <path-to-log>
   ```
3. Check the log for `error CS` (compile errors) or exceptions before assuming success. `[SceneBuilder] IterationRoom scene built at ...` and `[SceneBuilder] MainMenu scene built at ...` near the end, plus exit code 0, means it worked. Benign noise to ignore: `[Licensing::Client] Error: HandshakeResponse...` retries at startup that self-resolve.
4. To actually see/play it, launch the Editor GUI directly (Unity Hub's "Open" project picker has been flaky on this machine — "프로젝트를 찾을 수 없습니다" even on a valid project — so prefer launching the Editor binary directly):
   ```
   "C:\Program Files\Unity\Hub\Editor\6000.5.7f1\Editor\Unity.exe" -projectPath "C:\Users\seonl\Desktop\c\2026\summer\Iteration"
   ```
   Then open `Assets/Scenes/IterationRoom.unity` and hit Play. Check `Get-Process Unity` before launching a second instance — batchmode against a project already open in the GUI will conflict.

**Player Settings → Run In Background is ON**, and needs to stay on. Without it, play mode stops ticking the moment the Editor loses focus, so any MCP-driven test (teleport the player, open the door, screenshot) captures a stale frame and looks like the change did nothing — `Time.time` sits at ~0.04 while wall-clock seconds go by. `SceneBuilder.Build()` sets it, because setting it *during* play mode does not persist.

Once Unity MCP is connected in a session, prefer it for incremental/visual tweaks (moving objects, tweaking materials interactively) over round-tripping through `SceneBuilder.cs` + batchmode. Keep `SceneBuilder.cs` as the source of truth for anything structural, though — it's what makes the whole scene reproducible from scratch.

## Scene layout (current coordinates, all under namespace `IterationRoom`, room shell built in `Assets/Editor/SceneBuilder.cs`)

- **Three rooms in a line**, built by the same `BuildRoomShell` at different Z centres: `Room1` (the loop room, centre Z=0), `Room2` (centre Z=`RoomPitch`=10.85, i.e. `RoomDepth 10.5 + 2×WallDepth 0.125 + DoorPocketDepth 0.1`) and `Room3` (centre Z=`2 × RoomPitch`=21.7). Each shares a divider with the next — one room's north wall and its neighbour's south wall sit back to back with the same doorway cut out of both the panelling and the collision, making a walk-through passage. Scene paths are `Room/Room1/...` etc.; furniture and pads still hang off `Room/` directly.
  - Adding Room4 is `BuildRoomShell` at `3 * RoomPitch`, `BuildCeilingLights`, `BuildReflectionProbe`, and Room3's `BuildDoorPocketFill(..., capFarSide:)` going false with a new capped one behind it. **279 wall panels across the three**, up from 182.
  - Floor/ceiling slabs span the full `RoomPitch`, not just the interior, so adjacent rooms' floors meet exactly under the divider. Sized to the interior they leave an open gap at the threshold and the player drops through it.
- Room bounds (each room): X -4.375..4.375 (width 8.75), Z ±5.25 about its centre (depth 10.5), height **5.408**. Door, bed, and spawn all share the X=0 axis (centered layout). `BuildRoomShell`'s minZ/maxZ are derived as `zCenter ± depth/2` — don't hardcode them, it'll decenter the room.
  - **`GridCellHeight` is derived from the height, not the other way round** — `RoomHeight / GridRows`. At 4.5m (back when the cell was a hardcoded 1m) the top row was a half cell and the panelling ran off cut in half at the ceiling; deriving it makes that failure impossible. To change how tall the cells are, **change `GridRows`**, not the cell.
  - The height itself is the odd number it is because the **golden-ratio pass** left it there — see the wall-grid note below. It is kept rather than rounded because the fixture intensity and both reflection probes are tuned against it.
- Bed centered at (0, 0.7) (X/Z) — head/pillow end at high Z (near the door), foot at low Z (near spawn). It is `messy_bed.glb`. The model ships with **two pillows**, both off the centre line; `UseSinglePillow` hides one and slides the survivor onto X=0. They're separate nodes in the glb, so that's a transform tweak — a future bed model that bakes its pillows into the bedding mesh couldn't be fixed this way.
- Nightstand (`nightstand.glb`, with a lamp and vase on it) sits at (-0.95, 1.35), tight against the bed's west side and level with the pillow. It replaces the bedside table that came bundled with the previous bed model.
- Floor button sits in the open floor area past the foot of the bed, east side, around (2.8, -1.75) — also per `room_layout_sample.png`.
- The door is centered on the north wall (Z=5.25), X=0. It has no control beside it — see `Door`. The door is a **natural size (`DoorWidth` 1.3 x `DoorHeight` 2.5) and deliberately NOT snapped to the grid** — an earlier version forced it to exactly one cell wide and two tall, which read as a missing panel rather than a doorway. Instead the panelling is cut around it: `BuildShell` passes a doorway `Rect` to `BuildPanelWall`, and `SubtractRect` splits any panel that overlaps it into up to four surrounding pieces, so panels frame the door at whatever size it is.
  - The door **slides right into a pocket** (`Door.openLocalOffset` = +X by `DoorWidth`). The slab sits in the `DoorPocketDepth` cavity between the two rooms' walls, so sliding it sideways tucks it inside the wall build-up and both walls hide it. Room2's `KeyLock` plate is deliberately on the **left** (`-GridCellWidth`) — on the right it ends up buried behind the open slab.
  - **`BuildDoorPocketFill` caps the pocket** everywhere except the volume the slab actually sweeps (`X -0.66..1.96, Y 0..2.51`, i.e. closed position through open position plus 0.01 clearance so the fill's faces aren't coincident with the door's). Left as one open cavity the pocket ran the full width of the building and **exited to the sky at both ends** — standing in the doorway and looking sideways showed a 0.1 x 5m slot straight to the outside. It also gives the opening a real reveal instead of a hollow slot at the jamb. The fill carries no colliders: the walls either side already hold the collision, and the only route into that volume is the gap the fill deliberately leaves.
  - The doorway is cut out of the **backing slabs as well as the panels** (both are built from `SubtractRect` pieces). With the backing left as one solid slab the opening was a dead-end recess — collision was already cut so you could walk "through", but you were looking at wall.
- Bed spawn point (loop reset location) sits hard against the foot of the bed at **(0, -0.7), facing 180° (-Z)** — away from the bed, down the open room, as if you have just got up off it.
  - It used to be at Z=-1.75, which put the player 1.42m past the foot of the bed. The wake-up sequence poses the eye as if lying down and then sits you up, so it ended with the bed nowhere near the player and the whole thing failed to read as waking up *in* the bed. **Only the position was wrong** — the 180° facing was tried both ways and kept, since looking down the room reads as having got up, where facing the bed reads as standing at the foot of it staring at the mattress.
  - **The player cannot be spawned in the bed.** `PlaceModel` gives it a full-volume `BoxCollider` (measured: X -0.63..0.63, Y 0..0.89, Z -0.33..1.73), so a CharacterController placed inside spawns interpenetrating and gets shoved out on the first frame. With the bed's foot at Z=-0.33 and the controller's radius 0.3, **Z=-0.7 is as close as it can stand** (0.075m clearance, verified with an overlap query). Keeping X=0 preserves the deliberate door/bed/spawn centre line.
  - Measured landmarks if this ever needs re-tuning: mattress top Y=0.59, pillow centre (0, 0.59, 1.47), nightstand X -1.23..-0.67 / Z 1.16..1.54 (so the bed's **west** side is blocked and its east side is free).
- **Room2 is a different puzzle from Room1, and deliberately not another pad-and-button.** The chain is: the **nightstand drawer** in Room1 (E to open) holds a **pin tool** (E to take, held in hand) → walking into Room2 drops **70 pink balloons** from the ceiling → swinging the tool (left mouse) bursts them → one balloon holds the **key** → the key opens Room2's north **key door** (E at the lock).
  - **Balloons are physical, but a pop is recorded by *identity*, never by position** (`RecordedTimeline.PopEvent` carries a balloon id). This is the decision the whole thing rests on. Recording "the player swung here" and replaying it against physics that has moved everything makes a ghost's contribution a matter of luck; recording "the player burst balloon 17" means the ghost bursts balloon 17 wherever it has ended up, so progress accumulates exactly.
    - The cost, accepted knowingly: a ghost can swing at air while a balloon bursts across the room. It is tolerable because **ghosts have no colliders**, so the only thing scattering the balloons differently each iteration is the living player, and because nobody eye-tracks one balloon among seventy.
    - Pops are an **event list, not more bits in `RecordedFrame.signals`**. There are more balloons than the mask is wide, and a signal is a *level* (see `GhostInteractable`) whereas a pop is an instant with an identity on it. `GhostReplayer.DrainPops` fires every event whose time has passed, so an event survives a ghost skipping frames without the pulse-stretching `Drawer` needs. **It drains before the end-of-timeline check** — after it, one long frame would retire a ghost with its closing pops unfired and those balloons would stay up for good.
  - **The balloons are translucent, and the key is visible inside the one that holds it.** This is what makes the search a matter of looking rather than of bursting seventy and hoping — it was luck in the first version and it is now skill. `MakeTranslucentMaterial` is the URP transparent set-up on **Lit** rather than Unlit (unlike `GhostFaint`), because unlike a ghost these are real objects that have to take the ceiling lights; the blend modes **and** the `_SURFACE_TYPE_TRANSPARENT` keyword are both required or the alpha does nothing. The in-balloon key is a **child of the balloon**, so `SetInPlay` hides and shows it with everything else and it vanishes the instant the balloon bursts. It is deliberately a **darker** material than the loose key — at brass it washes out through the pink and stops being a shape.
  - **Balloon physics is hand-rolled falling, not gravity.** `useGravity` is off and `Balloon.FixedUpdate` applies `fallAcceleration` (2.2 m/s²) itself, with damping down at 1.1 and a bouncy `PhysicsMaterial` (0.55, `bounceCombine` **Maximum** since the floor and walls have no material of their own). Unity has no per-body gravity scale, and the alternative — damping a full 9.81 down to a drift — takes so much damping that the balloons stop bouncing and start behaving like they are underwater. **Low damping plus a small pull is light *and* lively; heavy damping is only slow.** Terminal velocity works out at 2.0 m/s.
  - **The player never collides with a balloon at all.** Balloons are on their own physics layer (`SceneBuilder.EnsureLayer("Balloon")`, index 8) which the `CharacterController` excludes via `excludeLayers`; they are still solid to each other, the floor and the walls. Pushing is therefore an explicit `OverlapCapsule` in `FirstPersonController.PushOverlapping`, not `OnControllerColliderHit`.
    - **This is the fix for "standing on a balloon lifts you into the air", and it was chosen over the one-line version on purpose.** The old push derived its direction from `hit.moveDirection`; standing still, the controller's only motion is gravity, i.e. `(0,-1,0)`, so both horizontal components were zero and the token lift meant to roll a balloon over your foot normalised into a **pure upward shove**, re-applied every frame. The balloon rose, `stepOffset` walked the player up onto it, and you rode it to the ceiling. Guarding the lift would have fixed that instance; removing the contact removes the class — there is nothing to stand on and nothing to be lifted by. Nothing else in the room stands on them, since ghosts have no colliders.
    - **Pushed by speed, not force, and horizontally only.** A capped `VelocityChange`, applied at the centre of mass (off-centre mostly spins a sphere) along the horizontal offset from the controller's axis to the balloon — geometry, not direction of travel, so it is well defined however the player moves and always points outwards. An early version applied an 0.55 impulse to a 0.04kg balloon: an 11 m/s kick off a brushed shin. The cap also means walking through a crowd nudges each balloon once instead of accelerating it every frame of contact. No lift component at all: nothing is under the player's foot any more.
    - The sweep is skipped entirely while the player has no horizontal input, and `horizontalMove` is **cleared when `ControlEnabled` goes false** — the wake-up takes control mid-stride, and a stale vector would leave the player blowing balloons apart with their eyes shut.
  - **The balloons are a pool, never instantiated at runtime**, because that is what makes an id mean the same thing sixty seconds later. Spawn points and the key balloon (**index 52**) both come from one fixed seed (`fieldSeed` 20260810) — reseed per iteration and the room becomes a different room each time, with nothing to learn.
  - `BalloonField` **parks the pool during `Build()`** (`ComputeSpawnPoints` is public for exactly this). Built objects sit at their parent's origin, which for these is the middle of Room1 — left to `Awake`, the saved scene stores seventy balloons heaped beside the bed and only play mode clears it. The reflection probes are unaffected either way: `BuildShell` bakes them before `BuildBalloons` runs.
  - `Balloon` resolves its own components through **`EnsureRefs()` rather than `Awake`**. Awake order between objects is undefined and `BalloonField` resets the whole pool from its own `Awake`; reached first, every reference would still be null and the reset would silently do nothing.
  - **The drop is triggered by anyone walking in — the player *or* a ghost** (`TriggerIfInside`). Ghosts are deterministic, so once one has been through that door the balloons come down at the same instant every iteration, which is what keeps later recordings aligned with the field they were made against.
  - **Carrying is world state and the loop rewinds it** (`PlayerHand.ReturnAll`, called from `RunLoop` *before* `BalloonField.ResetField` so the key is handed back and then hidden, not the other way round). Leave the tool in the player's hand across a reset and the trip to the drawer stops costing anything, which is most of what this puzzle is made of.
  - **The drawer is generated geometry.** `nightstand.glb` bakes its whole body into one mesh (`Nightstand_Nightstand_0`) — there is no drawer node to pull out. `BuildNightstandDrawer` measures that renderer's bounds (**min (-1.23, 0, 1.16), max (-0.67, 0.59, 1.52)**, logged on every build) and sizes a drawer onto the front face, which is the **-Z** one, facing the foot of the bed where the player wakes up looking.
  - The tool gates on `Drawer.**IsFullyOpen**`, not `IsOpen`. One E press would otherwise both open the drawer and empty it, with script execution order deciding whether it worked — which reads as the item being unobtainable half the time.
  - **`ghostInteractables` is `{ floorButton, drawer, pad3A, pad3B, pad3C, pad3D }` — six entries: Room1's pad, Room2's drawer, and Room3's four pads.** Append to this array, never reorder it: an entry's index is its bit in `RecordedFrame.signals`. The drawer pulse-stretches its signal (`openPulseDuration` 0.15s) because opening is an instant and a ghost can skip frames, and routes a ghost's replayed pull straight to `Open()` rather than back through the player's `Register…` path — otherwise each iteration re-records the last one's pulls and the drawer opens earlier and earlier until it opens on frame one.
    - The door button used to sit between the two and went with it; the drawer therefore moved from bit 2 to bit 1. **That was only safe because timelines live for one session of play and are never persisted** — reordering this at runtime invalidates every recording made so far.
  - **The key lock is deliberately NOT in that array, and the reasoning is the most important thing in this section.** The rule the whole room runs on is *record the attempt, re-evaluate the condition* — and that only holds while the condition being re-evaluated is **the one that actually enabled the action**. For the key door what enabled it was the player **holding the key**. A version of this shipped briefly that re-evaluated a ghost's unlock against `BalloonField.KeyRevealed` — the key's balloon having burst — which is a different and much weaker fact, and it quietly let a ghost do the one thing a ghost demonstrably cannot: carry something. Ghosts have no colliders and no inventory by design. `KeyRevealed` was removed along with it.
  - **Inserting the key is literal.** E at the lock while carrying it calls `PlayerHand.Surrender`, which drops it from the carried set (so `Has("Key")` goes false and the HUD loses the icon) but **keeps it in `taken`**, so `ReturnAll` still rewinds it. `CarryableItem.InsertInto` then parents it to a `KeySocket` on the lock plate and makes it visible again. The point is that "a ghost cannot do this" becomes something you watch happen rather than a rule written in a file.
    - **The key does not stay in the lock across the loop.** That was on the table — un-rewound world state would have made Room2 cheap to re-cross — and it was decided against: the loop rewinds the key like everything else. The consequence is real and is the thing to weigh before building Room3: **Room2's exit costs the *player* a balloon search in every iteration that wants to go past it, and that toll never accumulates the way Room1's pad does.** Whatever goes beyond Room2 has to be reachable by someone who has just spent most of their sixty seconds getting through it.
  - `DoorIndicator` gained an optional `keyLock` so the lamp over this door reports "you are carrying the key" the way the other reports "the pad is held". It goes red again the moment the key is surrendered, but by then `door.IsOpen` is holding it green.
  - **The lock's face is a keyhole, not a key.** `BuildKeyShape` still draws the silhouette twice — lying on the floor once its balloon bursts, and seen through the skin of the balloon that holds it — but the plate on Room2's wall now gets `BuildKeyholeSlot` (a round seat and a narrow slot, both flat decals on the face rather than a bored hole, which would show the wall behind). The etched key said what the lock wanted, which was right while nothing could ever be put in it; with a real key now sitting in the socket, an inserted key on top of an engraved one reads as two keys.
  - **Room3's north doorway is capped** (`BuildDoorPocketFill(..., capFarSide: true)` → `FarCap`), because there is nothing behind it yet. The cap **keeps its collider** — it is the end of the world, and the player must not walk out of the door they just opened. Room2's cap came off when Room3 was added; there is exactly one `FarCap` in the scene at any time, on the last room.
  - `BuildDoor` was split into `BuildDoorShell` (slab, pocket, lamp — shared) plus `BuildPadDoor` / `BuildKeyDoor`. The shell's root carries the room's Z offset so every measurement inside stays in the frame it was tuned in when there was one door. `LoopManager.door` is now `doors[]`.
- **Room3 is four floor pads and one door that needs ALL FOUR held at once** (`FloorButton3A`..`3D` at (±3.2, 18.7) and (±3.2, 24.7), `Door3` on the north wall). One person cannot stand in four places, so it takes **four past selves overlapping in time** — which is the thing Room1 does not ask for. Room1 proves a past self can do a job; Room3 asks you to make four of them do it *simultaneously*.
  - **It is deliberately the plainest room of the three — no items, nothing to search, nothing to carry — and that is a consequence of Room2, not laziness.** Room2's exit costs the *player* a key retrieval in every iteration that wants to go past it (see the key-lock note), so a second expensive room behind it would be unreachable rather than hard. What Room3 costs is **iterations**, not seconds: one per pad, plus one to walk through while four past selves hold them. Each of those visits is "walk in, stand on a pad", which is about as cheap as a room can be in clock time.
  - The pads are a **rectangle, not a scatter**. Four things in a regular grid read as one set at a glance — the player must never have to hunt for the fourth — and the symmetry says *all of these*, where an irregular arrangement invites guessing that some subset might do. All four sit off the centre line, so the straight walk from the south door to the north one steps on none of them.
  - **`FloorButton.AllActive(pads)` is the rule, and it lives in one place on purpose.** `Door` and `DoorIndicator` both call it, so the lamp can never say "go" on a rule the door does not use. A null or **empty** array is deliberately *not* active — a door wired to no pads should stay shut, where "all zero of them are held" would vacuously mean open.
  - The lamp is doing more work here than anywhere else: at Room1's door "red" means nobody is on the pad, but at Room3's it is the only way to tell **three** past selves having arrived from **four**.
  - Expect the player, in the final iteration, to arrive at Room3's door **before** the ghosts reach their pads — each iteration gets faster as the rooms ahead get solved by ghosts, so the recordings are slower than the run replaying them. Standing at the door watching four past selves converge is the intended beat, not a bug. It is also why the ghosts' `EndCycleControl` timing matters: a ghost that quit at t=40 releases its pad at t=40.
  - **Room3 is also where the room finally explains the end-cycle control** (`Room/PanelMessage.cs`, built by `SceneBuilder.BuildWallMessage`): `H O L D   [ N ]` / `TO SKIP TO THE NEXT ITERATION`, on **all four walls at once**, with the PA saying "Manual termination available. Hold N to end the cycle."
    - **On the wall rather than on the HUD, because the walls are displays** — that was established long before there was anything to display (the panel grid boots at the top of every iteration, which is what makes it a screen rather than tiling), and this is the in-fiction option CLAUDE.md had been pointing at as the best and most expensive one. A fifth grey disc on the HUD would have said the same thing in the game's voice instead of the facility's.
    - **Room3 rather than Room1, because that is where the information becomes worth having.** By the time a player is setting up four pads, every iteration costs a walk through two solved rooms and the dead time at the end is the most expensive thing in the run. Told this in Room1 they would have no use for it yet.
    - **Four walls, and that is not decoration.** The player enters through the south wall with their back to it, walks a diagonal to a pad, and turns to face the door — there is no single wall they reliably look at, and a message on the wrong one is a message nobody reads.
    - **The walls light up every visit; the announcement fires once per session.** A sign can sit there being true, but a voice repeating an instruction the player has already followed, across all several iterations they spend crossing this room, would become the most irritating thing in the prototype.
    - Not the panels themselves spelling it out — that was the first idea and the grid kills it. A wall is 5 or 6 cells across by 4 tall, so panel-as-pixel is a **6x4 display** and nothing legible fits. What still makes it read as the wall rather than as a poster is the **dark plate behind the type**: a section of white panelling switching to near-black with red text on it is what a display doing something looks like, and it is the same red-on-near-black the HUD already uses.
  - **Four pads sets the run's floor at about seven iterations** (Room1's pad, Room2's key balloon, four Room3 pads, then the escape). That is the number to weigh if the pad count ever changes, and it is also what makes the missing **ghost reset** (next steps §2) press harder than it did — seven ghosts are in the room by the end.
- **Lighting comes from four recessed ceiling fixtures per room** (`SceneBuilder.BuildCeilingLights`) — emissive panels plus real spot lights, in a 2x2 grid (X = ±`GridCellWidth`, Z = centre ±2.6).
  - **This replaced an all-ambient setup, and that swap is the whole reason the room stopped reading as a whitebox.** It used to be lit by flat ambient at (0.95, 0.95, 0.97) with *no lights in the room at all*. Flat ambient adds the same amount to every surface regardless of orientation, distance or occlusion, so wall, ceiling and floor came out identical: no falloff, no direction, no contrast, nothing to read depth from. If the room ever looks flat again, check whether something has pushed ambient back up to carry the lighting.
  - **Spots, not points**, aimed straight down: a downlight's cone is what gives the floor bright pools and lets the walls fall off toward the corners, and that gradient is most of the effect. `spotAngle` 130 / `innerSpotAngle` 45 so it behaves like a panel rather than a torch.
  - `intensity` **10.5**, and higher than it looks because a 130° cone from over 5m up spreads over most of the room: at 4 the room came out dim grey. It has moved three times for three reasons — 11 with six fixtures, 15 when the count dropped to four, 9 once the ambient fill was cut back (the fill had been carrying more of the lighting than it looked), and 10.5 when the golden-ratio grid raised the ceiling.
  - **That last figure is derived rather than tuned**: the fixtures went from 5.0m to 5.408m, and `9 × (5.408/5.0)² = 10.5` holds the floor at the brightness that was signed off at the lower ceiling. Inverse square is only an approximation here — the cone also spreads wider from higher up — so it is a starting point to check by eye in play mode, not a measured value. If the fixture count, the ceiling height or the ambient bands move again, this has to move with them.
  - **Only Room1's fixtures cast shadows.** Every additional light's shadow shares one atlas, and the rooms past the first hold nothing worth the map: Room2 is balloons, Room3 is two floor pads.
  - **The default Directional Light is deleted, not dimmed.** These are sealed boxes with a ceiling slab; a sun has no way in, so it contributed exactly nothing while still costing a shadow pass.
- **Ambient is `Trilight`, not `Flat`**, and is demoted to standing in for the bounce URP is not computing. Trilight lights a surface by which way it *faces*, which maps directly onto the one thing downlights get wrong — they hammer the floor and never touch the ceiling.
  - `ambientGroundColor` **(0.719)** lights **downward** faces, i.e. the ceiling. Nothing else in the room lights an upward-facing surface at all.
  - `ambientEquatorColor` **(0.644)** → the walls. `ambientSkyColor` **(0.155)** lights **upward** faces, i.e. the floor, which the spots already cover — raise it and the floor blows out.
  - **Tuned by eye in play mode over two passes on 2026-08-10**, from 0.22 / 0.40 / 0.88. The shape that came out: floor lowest by a long way, walls and ceiling high and close together. The walls went *down* to 0.138 in the first pass and back **up** to 0.644 in the second — at 0.138 the spots' falloff toward the corners read as gloom rather than as shape, and the room lost the clinical evenness it is supposed to have. The fixtures came down 15 → 9 across the same passes: the fill had been carrying more of the lighting than it looked.
  - Expect the ground colour to bleed onto the walls; that is spherical harmonics doing what bounce would, and it is why the walls read lit rather than painted.
  - **`DynamicGI.UpdateEnvironment()` must be called after assigning these.** Without it the values are stored but never reach a shader, and every tweak looks like it did nothing — this wasted a full tuning pass.
- **The brightness numbers above were found in play mode, not by rebuilding between guesses.** An in-play IMGUI panel (`Dev/LightingTuner.cs`, `F1`) drove the fixture intensity, the three Trilight bands and post exposure, and copied a paste-ready C# snippet to the clipboard. It was always scaffolding and it has now been **deleted** — the values are settled and live in `SetupLighting` / `BuildCeilingLights`, which were always the source of truth.
  - Two things it taught, worth keeping now the tool is gone. A tuning panel must **seed its controls from the live scene**: hardcoded constants meant that opening it silently *overwrote* the room's real lighting on the first frame, so the room jumped back to its old brightness and the copied snippet reported the constants rather than anything that had been tuned — it reads exactly like "my change never went in", and it cost a pass before the cause was spotted. And it must hold `ControlEnabled` false **every frame** rather than once on open, since the loop hands control back at the end of every wake-up regardless.
  - If one is ever needed again, `git log -- Assets/Scripts/Dev/LightingTuner.cs` has it. Touch `volume.profile`, **not** `volume.sharedProfile` — the former hands back a runtime clone, so dragging exposure in play mode cannot quietly dirty `IterationVolume.asset` on disk.
- URP gates non-main lights behind the pipeline asset, reconciled by `SceneBuilder.ConfigureLightingPipeline()`. **Its enums are set by name, never by index**: `m_AdditionalLightsRenderingMode` serialises as `[Disabled, PerPixel, PerVertex]`, so PerPixel is index **1**, not the 2 you would guess — picking 2 silently gives per-vertex lighting, which washes the room into flat blocks. `m_AdditionalLightsShadowmapResolution` is likewise an enum (`_256`…`_8192`), so assigning `2048` as an int throws "enum index is out of range". It is set to `_4096` because six shadowed fixtures at `_2048` make URP log "Reduced additional punctual light shadows resolution by 2" and quietly drop each map to 512.
- Post-processing (`SceneBuilder.BuildPostProcessing`) is a global `Volume` in the scene pointing at `Assets/Settings/IterationVolume.asset`: Neutral tonemapping (ACES crushes the near-white walls to grey and warms them), a subtle vignette, contrast +8, and a deliberately high bloom threshold of 1.2 — the walls sit near 1.0 luminance, so a default threshold blooms the whole room. The player camera opts in via `UniversalAdditionalCameraData.renderPostProcessing`; URP cameras ignore the volume stack otherwise.
- Ambient occlusion is a **renderer feature on `IterationRenderer.asset`, not a volume override**, so it lives outside the scene. `SceneBuilder.ConfigureAmbientOcclusion()` reconciles it on every build because adding it is not idempotent — a retried add silently stacks duplicates (this already happened once, producing six SSAO features). Settings that matter:
  - **`Samples`, `NormalSamples` and `BlurQuality` run `High=0, Medium=1, Low=2`, i.e. 0 is the best quality, which reads backwards.** Setting `Samples` to 2 drops it to 4 samples and sprays visible occlusion noise around every object.
  - `Radius` is the other half of the noise problem, and the two were fixed in separate passes. The stock 0.035m reads as no occlusion at all here, but 0.12 throws a broad dithered halo around small objects (the key-lock plate, door edges) which on flat white walls reads as *dirt*. 0.045 with `Intensity` 0.7 and `AOMethod = InterleavedGradient` is the clean point: tight contact shadows only.
  - If the scene ever looks "dirty/noisy around objects" again, it's this feature, not the lighting.
- All room materials are matte (`_Glossiness` 0.03) and `RenderSettings.reflectionIntensity` is 0.1. Standard's default 0.5 smoothness mirrors the blue procedural skybox onto the walls/floor, which reads as a weird blue tint.
- **Wall grid cells are 1.75m wide x 1.3519m tall** (ratio ≈ 1.29), 5 columns on the end walls, 6 on the sides, **4 rows**. 88 panels per room, **182 across both** once the doorway splits some of them.
  - Two hard constraints sit behind those numbers. A cell's *width* has to divide both 8.75 and 10.5 exactly, or the last column of a wall overshoots its end (`BuildPanelWall` lays cells at fixed `GridCellWidth` steps after rounding the column count). A cell's *height* has to divide `RoomHeight` exactly — which is now enforced by construction rather than by care, since the cell height is derived from it.
  - **The cells were briefly exactly φ:1** (1.75 × 1.0816, five rows), and that pass is where `RoomHeight`'s odd 5.4078 comes from. Worth keeping the reasoning: an exact φ cell and a fixed room *cannot* both hold, because both constraints above demand a rational ratio and φ is irrational. The height was the cheapest thing to move — the floor plan carries the bed, nightstand, pad, spawn and door, all placed by eye against a film still, where the ceiling carries four fixtures with one tuned number between them. The ratio went when the cells were made taller; it could not have survived that anyway, since φ fixes the height and the change asked for a different one.
  - The alternatives, if φ is ever wanted back: rebuild the floor plan around it (room 8.75 × 10.5 → **8.09 × 9.71**, moving all the furniture), or approximate with a rational cell that still tiles — the closest is **0.583 × 0.357**, +0.95% off φ and visually indistinguishable, but it takes the panel count from 110 to 924 per room and `WallPanelDisplay` drives every panel through its own property block.
  - Groove width is `GridLineThickness` **0.05**, leaving a visible panel face of **1.70 × 1.3019m**. It was 0.082 when the cells were shorter: the taller the panel, the more groove it takes to hold the same visual weight. Shrink the cells much and it has to come back down, or the panels turn to slivers — pieces under 0.02m are skipped outright.
- **There is no grid texture any more.** The grid is entirely geometry: white panel cubes over a near-black backing (`GrooveDark`), so what shows at the bottom of each groove is the dark backing. The old `WallGrid`/`WallGridSide` textured materials, their 2048px baked texture and all the tiling/offset maths were deleted when the backing had to be split into pieces to cut the doorway — a split slab can't carry a tiled texture correctly, since each piece's UVs run 0..1 across *itself*.
- **The player camera's near clip plane is 0.05, not Unity's default 0.3** (far is 100, not 1000). This is not a tuning preference — at 0.3 you could stand against a wall or the door, turn sideways, and see straight through to the far side of the room. What pokes through a surface is the near plane's **corner**, not its centre: at fov 60 that corner reaches **0.463m** (0.532m ultrawide), while the CharacterController only stops the camera **0.220m** away (radius 0.3 minus skinWidth 0.08, which lets the wall penetrate the capsule). The entire wall build-up is `WallDepth` = 0.125m, so the frustum cut clean through it. At 0.05 the corner reaches 0.077m — a 2.8x margin at 16:9, still 1.9x at 32:9. **If the fov is ever raised, re-check this**, since the corner scales with `tan(fov/2)`. The far plane came in from 1000 to concentrate depth precision on a ~22m scene, which also helps SSAO resolve the 0.025m grooves.
- The floor/ceiling slabs are pushed **out by half their thickness** so their inner faces sit exactly on the room bounds, rather than sinking half the slab into the room.
- **Walls are real panel geometry, not just a textured plane** (`SceneBuilder.BuildPanelWall`). Each wall is a recessed backing slab plus a grid of raised panel cubes, so the seams are actual grooves (`GrooveDepth`) that catch shadow and ambient occlusion. Two things to know before touching it:
  - Neither the panels nor the backing slab carry colliders. Collision is a **separate set of invisible boxes** built by subtracting the doorway from the wall rect (same `SubtractRect` used for the panels). A collider on the backing slab would be `GrooveDepth` too far back — the player walks past the panels and the camera's near plane clips through the wall — and it would also seal the doorway shut.
  - **Backing and collision overrun both ends of the wall by `WallDepth`** (`structureRect`), so adjacent walls interpenetrate at the corners. Sized to the interior exactly — as they originally were — two perpendicular walls meet along a *line* and leave a `WallDepth`-square column, full room height, that neither covers. A raycast never finds it (the void sits behind a zero-width seam, and 120,000 sampled directions from inside the room all hit something), but rendering two slabs that merely touch produces pinhole cracks at grazing angles. **This is also why thickening the walls is the wrong fix for see-through: the void is `WallDepth` squared, so a thicker wall makes it bigger.** The panel grid stays at the interior width, so the visible cell layout is unchanged and the overrun is buried inside the neighbouring wall.
  - `GrooveDepth` is a tradeoff, not a free parameter: deeper catches more occlusion, but the panels' white side faces then wash the seam out when you view a wall at a grazing angle. 0.025 is the balance point found by eye.
- Countdown timer text (`CountdownTimer`, top-right) is red (`Color.red`).
- **The HUD is monospace** — `Assets/Fonts/JetBrains_Mono/static/JetBrainsMono-Regular.ttf`, resolved by `SceneBuilder.UIFont()` and used by every text object in both scenes.
  - Diegetic reason: everything on screen belongs to the *facility* rather than to the player — the iteration number, the clock, the control that ends a cycle — and a terminal face says so where a proportional one reads as the game's own UI. The room is built out of wall displays for the same reason.
  - Practical reason: the countdown changes every second, and in a proportional font its digits are different widths, so it reflows and twitches on the spot every tick. Monospace holds still.
  - **Licensing: JetBrains Mono is SIL OFL, and `OFL.txt` ships next to it in `Assets/Fonts/JetBrains_Mono/`.** Keep that file where it is — the licence requires it to travel with the font.
  - This **replaced Consolas**, which was Microsoft's, copied out of `C:/Windows/Fonts`, and fine only for a prototype that never left this machine. It was swapped the moment a build was going to be handed to other people. If a font is ever changed again, that is the bar: embedding it in a distributed build is redistribution.
  - Point `UIFont()` at the **static Regular**, never the variable font that ships beside it — uGUI's legacy `Font` has no axis control, so a variable face is a coin toss on which weight renders. The other 19 weights in the folder are unreferenced and therefore not built; they cost nothing but disk.
  - `UIFont()` falls back to the built-in font rather than throwing, so a missing file leaves the UI ugly and legible instead of unbuildable. **Check that it did not fall back** after a font change: `grep -o "m_Font: {fileID: [0-9]*, guid: [a-f0-9]*" Assets/Scenes/*.unity | sort | uniq -c` should show one guid, matching the new `.ttf.meta`.
- **The "Iteration N" label sits dead centre**, and is set upper case and spaced out (`IterationLabel.spacedCaps`). It used to sit 150px above centre, which read as a subtitle floating over the room — the label is the iteration announcing itself, so it gets the middle of the screen with nothing else on it. The spacing is done by putting a space between every character **in the string**, because uGUI's `Text` has no tracking control at all; in a monospace face that lands as exactly one cell, and the single space between the two words becomes three, which keeps the word break readable. `horizontalOverflow` is `Overflow` so a rect a shade too narrow can't break it as "ITERATIO / N 12".
- **`EndCycleControl` sits immediately left of the countdown.** It started as a test aid for skipping the 60-second wait, and was promoted to a real mechanic: **60 seconds is a ceiling, not a quota.** Once you have done what you came to do, the remainder is dead time, and spending it was the one thing the loop never let the player decide. Available from iteration 1 onward. (This is a deliberate departure from spec §4.3–4.4, which has the loop always run its full 60 seconds.)
  - **Its label was silently wrapping onto two lines, and that is probably why testers asked for a skip button it has had since the first build.** `HOLD [N] — END CYCLE` is 20 monospace cells, i.e. ~192px at `fontSize` 16, inside a rect that was **168** wide — so uGUI broke it in half and it read as decoration beside the countdown rather than as a control. The rect is now 224 and the `Text` is set to `Overflow` as well, since the scaler can shave a pixel at some resolutions. **Check any fixed-width HUD label against `0.6 × fontSize × length`**; this is the second time a label has quietly rewrapped.
  - **Room3 teaches it explicitly**, on all four walls plus a PA line — see the Room3 notes under **Scene layout**. Between that and the widened label, a player who never finds this control has been told about it three ways.
  - **Hold to commit** (`holdDuration` 0.6s, with a fill gauge), not press — it is irreversible and it truncates the recording the next ghost is made from, so brushing a key must not fire it. The control dims to `unavailableAlpha` whenever `LoopManager.IterationRunning` is false, so it reads as unavailable during the wake-up instead of broken.
  - Answers to **`N`** as well as a click, and the key is what actually gets used: `FirstPersonController` locks and hides the cursor, so clicking means freeing it first and then watching the view spin as the mouse drags to the corner. The scene also gains an **`EventSystem`** — uGUI is inert without one, and `NewScene`'s default objects are only a camera and a light.
  - `LoopManager.EndCycleEarly` sets a flag rather than shoving `ElapsedTime` to `loopDuration`, because `ElapsedTime` is the timestamp written into every recorded frame and forcing it would corrupt the tail of the timeline the ghost is about to replay. The flag is armed just before the timed window, so an input landing during the wake-up can't end the next cycle instantly; `EndCycleControl` re-arms only on release, so holding the key through the blackout doesn't chain.
  - The announcer says **"Cycle terminated."** on a voluntary end, because cutting the clock short skips the countdown — otherwise the one decision the player gets to make lands in silence.
  - **This mechanic only works because `GhostReplayer.Tick` releases everything once a timeline runs out — see below. Do not change that without re-reading this.**

## The ending (`Loop/EscapeTrigger.cs`, `Loop/EndingSequence.cs`)

Walking out of Room3's north door ends the run. It is the **only** exit condition in the game and the only thing that ever breaks `LoopManager.RunLoop`'s `while (true)`.

- **`EscapeTrigger` sits ON the threshold, not past it, and that is forced rather than lazy.** The `FarCap` is directly behind that doorway and the pocket in front of it is `DoorPocketDepth` 0.1m against a controller of radius 0.3 — **there is physically no "through" to stand in**. The volume is centred on Room3's north wall face (world Z 26.95, `halfDepth` 0.5), which a player can reach to Z≈26.875 before the cap stops them. The ending takes control on the frame it fires, so they never reach the wall and never learn it was there.
  - Two gates and both matter. **`door.IsOpen`**, so walking up to a shut door ends nothing — the pads are what open it, which makes this read as *you got out* rather than *you arrived*. And **`halfWidth` = `DoorWidth/2 + 0.05`**, because without an X bound anyone idling anywhere along the north wall is at the same Z as the opening, and the run would end from across the room the moment the fourth pad went down.
  - Y is deliberately **not** tested: the room has a floor and a ceiling, so anything at that X and Z is in the doorway whatever its height, and a jump must not be a way to miss the end of the game.
- **The ending is defined by what it does NOT do**, because the reset is the only vocabulary the game has built and the player has seen it dozens of times. A reset is: the room flares, the view judders, the lids blink shut, the panels go dark, it starts again. So:
  - **The collapse lets go instead of peaking.** `RunEnding` ramps flare and shake down from `WallPanelDisplay.Flare` (wherever the collapse had got to) rather than holding them at full. Escape inside `collapseLeadTime` and you watch the thing that takes you every sixty seconds try, and stop.
  - **The panels do not power down.** That is the loop's signature — the cell being switched off before being switched back on — and using it here would say the cycle continued.
  - **The lids do not blink.** The blink is involuntary; it belongs to the thing that just failed. `EndingSequence` fades its own opaque scrim instead. Reusing the eyelids would have been free and would have been wrong.
  - **The ghosts are left standing**, visible under the scrim as it comes up, holding their pads. That is the last image of the run: the people it took to get out.
  - **The room tone fades and stops** (`RoomAmbience.FadeOutTone`) — the only thing that ever stops it. It has been under every second of every iteration, so its absence is the quietest and clearest signal that this one is not turning over. It fades rather than cutting: a cut reads as a sound failing.
- Timing: scrim 2.4s → 0.9s of black → card 1.4s → hold 6.5s → `MainMenu`. **The return to the title is automatic, not on a keypress** — the player has finished, and a prompt would ask them to do one more thing in a game that has just stopped asking.
- The card is `C Y C L E   B R O K E N` over `ESCAPED ON ITERATION N`. The headline gets the spaced-caps treatment in the string, exactly as `IterationLabel` does it. The iteration number is the one score the game keeps, and it is diegetic — the facility counted them.
- **Everything in `EndingSequence` runs on `Time.unscaledDeltaTime`.** Pausing is locked out for the duration (`LoopManager.RunOver`, read by `PauseMenu`), but a coroutine that can be frozen with no loop left running to unfreeze it is a soft lock at the one moment the game must not have one.
- `RunEnding` **discards the final recording**. The run that got out does not become a ghost — there is no next iteration for it to haunt, and building one would be the loop's habit outliving the loop.

## The title screen (`MainMenu.unity`)

A separate, near-empty scene: a camera, a canvas, a still of the room, `PLAY` and `QUIT`. It is the entry point of a standalone build.

- **Separate scene rather than a state of the room, and that choice is what makes the loading bar real.** `IterationRoom` is a 306,000-triangle bed, 182 wall panels, seventy balloons, two baked probes and a pile of shaders — it takes a genuine moment. Held inside one scene there would be nothing to load and the bar would be theatre.
- **The background is a still of the game's own first frame**, `Assets/Textures/MenuBackground.png` — the player camera's view from the foot of the bed, which is exactly what the Editor's Game view shows before Play is pressed. `SceneBuilder.CaptureMenuBackground` renders it **on every build**, so the menu can never advertise a room that no longer exists.
  - Captured through `RenderPipeline.SubmitRenderRequest` with a `UniversalRenderPipeline.SingleCameraRequest`, **not** `Camera.Render()` — URP does not support a bare `Render()` from arbitrary code, and the request is also what actually runs the volume stack, so the still carries the same tonemapping, bloom and vignette the room is tuned against.
  - The camera's `targetTexture` is restored in a `finally`. Left assigned, the game would render into a `RenderTexture` instead of the screen — and the saved scene would carry it.
  - **Skipped under `-nographics`**, where there is no device to render with. The previous PNG stands and the build logs a warning: a stale background is a far better outcome than a failed build. To refresh it, build from the Editor (or without `-nographics`).
  - **Note what this view actually contains, and that it was kept on purpose.** The spawn faces *away* from the bed, so the still is the south wall's panelling and nothing else — no bed, no door, no furniture. It was offered against a dedicated framing that would show the room's contents, and the empty wall was chosen: it is the frame the game genuinely opens on, and a grid of blank panels says what this place is more plainly than a picture of the furniture would. If that is ever revisited, the change is a menu-only camera rather than the spawn one — do not move the spawn to improve the menu.
- `Loop/…`-style HUD language throughout: the same monospace face, red on a dark scrim, the title spaced out in the string exactly as `IterationLabel` does it (uGUI's `Text` has no tracking control, and in a monospace face a space is one cell). The menu and the in-game readouts then read as the same voice.
- **Buttons are white with the dark look coming entirely from the `ColorBlock`.** A `Button` tints its target graphic by multiplying, so a background that is already near-black has nothing left to brighten with on hover.
- `onClick` is wired in `MainMenu.Awake` from serialized `Button` references, **not** as persistent listeners. A listener added from an editor script has to go through `UnityEventTools` to serialize at all; this is one line and always works.
- The menu **puts the cursor back** (`Cursor.lockState = None`) in `Start`. `FirstPersonController` locks and hides it, and Unity does not reset that across a scene load — without this, coming back to the menu would leave something you cannot click.

## Mouse sensitivity, and why it is a setting (`Loop/GameSettings.cs`)

The first public play-test on itch.io came back with "the mouse is far too sensitive", from a build that felt fine in the Editor. It is not a tuning miss — **the same constant genuinely means different things on the web and on the desktop, and different things on two testers' machines.**

- **Unity's WebGL build hands the engine the browser's pointer-lock delta completely unscaled.** Verified by decompressing the shipped `Build/WebGL/Build/WebGL.framework.js.unityweb`: `fillMouseEventData` does literally `HEAP32[idx+8] = e["movementX"]` — no `devicePixelRatio`, no canvas-size correction, nothing. That value has already been through the OS pointer-speed slider and its acceleration curve on the way out of the browser, and Chrome, Firefox and Safari do not agree on it. The Editor's input path never goes near any of that.
- **It is not frame rate**, which is the usual first guess. `Input.GetAxis("Mouse X")` is already the delta accumulated *since the last frame*, so the per-frame values shrink as the frame rate rises and the total rotation over a given sweep comes out the same. That is also why `FirstPersonController.HandleLook` correctly uses **no `deltaTime`** — don't "fix" that.
- So the fix is not a better number. `mouseSensitivity` was a serialized field at **2.0**; it is now `GameSettings.MouseSensitivity`, default **1.1**, with a slider in the pause menu and `PlayerPrefs` behind it. The default is a starting point, not an answer.
- `GameSettings` **applies live but writes on the way out**, from `PauseMenu.Apply(false)`. A uGUI `Slider` raises `onValueChanged` every frame of a drag, and on WebGL each `PlayerPrefs.Save` is a storage flush. Nothing relies on `OnApplicationQuit`: a browser tab is *closed*, not quit, and Unity's WebGL shutdown path is not guaranteed to run.
- The slider is seeded with `SetValueWithoutNotify` **before** the listener is attached. A `Slider` raises the event on assignment, so seeding afterwards writes the slider's own starting value straight back over the saved one — the same trap the deleted `LightingTuner` fell into, and it reads exactly like "my change never went in".
- Still available if the defaults keep drawing complaints: request pointer lock with `{ unadjustedMovement: true }` through a `.jslib`, which bypasses the OS acceleration curve so the default means the same thing on every machine. Chrome and Edge support it; Firefox and Safari fall back silently. Not done — the slider makes it optional rather than necessary.

## Pausing (`Loop/PauseMenu.cs`)

**Escape** freezes the room and puts `RESUME` / `MAIN MENU` / `QUIT` over it, plus the mouse-sensitivity slider. Escape again resumes.

- **The pause overlay is also the settings screen**, and that is the right home for this particular setting rather than a compromise: it is the only place the player can reach with the cursor free *and* the room still in front of them. Resume, look around, pause again, adjust. `MakeSlider` in `SceneBuilder` assembles the `Slider` by hand — note that Unity drives the fill's and the handle's anchors itself every frame and finds their containers **through the hierarchy, not through fields**, so each must be the child of its own container rect with offsets left at zero, or the value it computes lands somewhere other than where it draws.

- **The freeze is one line — `Time.timeScale = 0` — and it works because every moving part here already runs on scaled time**: the loop's clock (`ElapsedTime += Time.deltaTime`), the wake-up's `WaitForSeconds`, the collapse ramp, the balloons' physics, and `CameraShaker`'s Perlin sampling of `Time.time`. None of them needs to know a pause exists. Verified by reading for `Time.unscaled*` before building it — there is none in the game code.
- **What a zero time scale does not stop is `Update`.** Every script that reads a raw key would still see it: `E` would open drawers, `N` would charge the end-cycle control, the mouse would swing the pin, and — worst of the lot — `FirstPersonController.HandleLook` uses **no `deltaTime` at all**, so the view would swing with the very mouse movement being made to reach Resume.
  - The gate is **`LoopManager.AcceptsInput`** (`IterationRunning && !IsPaused`). Everything that reads a key in `Update` gates on that rather than on `IterationRunning`; the two differ only while paused. `BalloonTool`, `Drawer`, `CarryableItem`, `KeyLock`, `EndCycleControl` and `ControlHintDisplay` were all moved onto it. **A new interactable that reads input must use it too.**
  - `ControlEnabled` is forced false **every frame** while paused, not once on open — the loop hands control back at the end of every wake-up regardless of what the menu wants. On resume it is restored to *what it was*, not to true, so pausing during a wake-up cannot hand the player a camera the loop had deliberately taken away.
- `AudioListener.pause = true` as well: the announcer and the room tone are not on scaled time and would carry on talking over a frozen room.
- **`Time.timeScale` and `AudioListener.pause` are global, not per-scene**, so both are restored in `OnDestroy` as well as on the way out through the buttons — that covers the scene change too, which is the path easiest to miss. `ToMainMenu` unfreezes *before* the load, since a scene that arrives at `timeScale 0` has no way to start itself moving.
- The overlay is **built last on the canvas** (sibling index 6, after `ControlHints`), so it covers the HUD, the prompts and the eyelids. Its scrim keeps `raycastTarget` on deliberately: that is what stops a click reaching the end-cycle control underneath. The `CanvasGroup` clears **`blocksRaycasts` as well as alpha** when closed — an alpha-0 graphic still receives clicks, so without it the invisible overlay would swallow everything the moment it had been opened once.
- `ControlHintDisplay`'s fade moved to `Time.unscaledDeltaTime` for this: on scaled time a prompt caught mid-fade would sit frozen under the overlay instead of going away.

## Scripts (`Assets/Scripts/`, namespace `IterationRoom`)

- `Player/FirstPersonController.cs` — CharacterController-based Portal-style movement + mouse look + jump (`jumpForce`, Space/`Jump` axis).
- `Loop/LoopManager.cs` — singleton driving the 60s loop. The whole loop is **one coroutine (`RunLoop`), not `Update`**: an iteration now opens and closes with the wake-up sequence, and the clock and the ghosts have to stay frozen while that plays. Recording deliberately starts only once the player has control, so every ghost's timeline covers the same window — start it before the wake-up and you get a pile of frames all stamped t=0.
  - **The `while (true)` has exactly one exit, and where it sits is load-bearing.** The escape check is taken immediately after `IterationRunning = false` and *before* everything that follows — the collapse held at full, the pull-in, the blink, the panels going out, the recording becoming another ghost. All of that is the cycle closing and re-opening, and none of it should happen to a player who just got out. See **The ending**.
- `Loop/WakeUpSequence.cs` — the transition between iterations: eyelids (two black UI panels driven through their *anchors*, so they cover any resolution) fall shut as time runs out, then open on the ceiling before the player sits up. It borrows the camera by clearing `FirstPersonController.ControlEnabled` and posing the eye via `SetEyePose(height, pitch, roll)`. Negative pitch looks up.
  - **The lids blink rather than sweep** (`blinkShutKeys` / `blinkOpenKeys`, each an array of `x = lid position, y = seconds`). Eyes don't close like a shutter: they fall, snap part of the way back, fall further, and only then give out. That flutter is what makes the loop taking you read as involuntary instead of as a fade-to-black transition. `lidPosition` is tracked so each keyframe starts from wherever the last one left off.
  - **The rise decouples body from head.** The body eases out (quick off the pillow, settling as it arrives) while the head lags a quarter of the way in and only levels once you're most of the way up, plus a slight `riseRoll` lean that leaves and returns to level. Driving height and pitch from one shared `SmoothStep`, as this originally did, is exactly what made it read as a camera on rails rather than a person sitting up.
- `Player/CameraShaker.cs` — sits on a **`CameraRig` between the player and the camera**, and that placement is the whole point: `FirstPersonController` rewrites the camera's own `localPosition` and euler angles every frame (look, and `SetEyePose`), so a shake applied to the camera itself is wiped instantly. Uses Perlin rather than `Random` — continuous noise reads as a building judder, per-frame random values read as a broken frame rate.
- `Interactables/DoorIndicator.cs` — the lamp above the door: one block split into a red half and a green half, only ever one lit (albedo *and* emission, since albedo alone just looks like coloured plastic). **It tracks the condition, not the door**: green the moment `FloorButton.IsActive` (or once the door is already open), so it becomes the puzzle's readout — the player can see a ghost step onto the pad from across the room instead of walking over to try the button. `Door` no longer owns any indicator state.
- `Loop/IterationLabel.cs` — fades the center-screen "Iteration N" text in/out. The eyelids are built first in `BuildUI` so they sit at the back of the canvas and the label/timer draw on top of the black rather than being covered by it.
- `Ghost/RecordedFrame.cs`, `Ghost/PlayerRecorder.cs`, `Ghost/GhostReplayer.cs`, `Ghost/GhostInteractable.cs` — records player position/yaw plus a **bitmask of interaction signals** at a fixed sample interval; ghosts scrub the timeline and report those signals back (not via physics — **ghosts have no collider at all**, so they can never trigger anything by touching it).
  - `GhostInteractable` is the abstraction: anything a ghost can operate exposes `PlayerSignal` (sampled into one bit) and `SetGhostSignal` (fed that bit back an iteration later). `FloorButton` and `Drawer` are the two implementations. **This was originally hardcoded to one `FloorButton`**, which meant a ghost's only possible contribution was standing on that one pad; generalising it is what let the drawer join later.
  - **Bit position is the object's index in `LoopManager.ghostInteractables`**, and `PlayerRecorder.interactables` must be the same array in the same order. `SceneBuilder` builds one array and hands it to both. Reordering it invalidates every timeline recorded so far.
  - **Signals are levels, not events.** A ghost advances its cursor by elapsed time and can skip several recorded frames in one tick, so a one-frame pulse would eventually be missed. Press-type interactables therefore stretch their pulse (`Drawer.openPulseDuration`, 0.15s) instead of recording an edge, and act on the rising edge at replay.
  - **A ghost releases every signal and hides itself once its timeline runs out** (`GhostReplayer.Tick`, guarded by `finished`). Clamping the cursor at the last frame — which is what the scrub loop does on its own — keeps applying that frame's signals for the rest of the loop. That was harmless while every timeline was a full 60 seconds, but `EndCycleControl` made short timelines possible and it becomes decisive: **quit at t=5s standing on the floor pad and the final frame's signal would stay applied from t=5 to t=60 of every future iteration** — five seconds of your time buying a 55-second hold, which deletes the "spend a whole iteration on this" premise the puzzle is built on. With the release in place, deciding when to quit *is* deciding how long your past self keeps standing there.
  - **Ghosts are hidden for the whole wake-up** (`GhostReplayer.SetVisible`, driven from `RunLoop`). Every timeline's frame 0 is the bed spawn, because recording starts the instant the wake-up hands control back — so `ResetPlayback` parks *every ghost ever made* on the exact spot the player is about to open their eyes on. They come back exactly as the clock starts, which is also the frame they start moving, so they appear already walking rather than blinking into existence. (They cast no shadows either way: the `GhostFaint` material's ShadowCaster pass is off, even though the renderers are still `castShadows = On`.)
  - **Only the real player's actions may raise a signal.** `Drawer.RegisterPlayerOpen` sets the pulse; a ghost's replayed pull goes straight to `Open()` and deliberately bypasses it. Route a ghost through the recording path and each iteration inherits every action of the one before — the drawer would open earlier and earlier until it opened on frame one.
  - The ghost is a **rough human silhouette assembled from primitives** (head/torso/2 arms/2 legs), not a capsule. It's held at alpha 0.16 near-black on an unlit transparent material (`GhostFaint`), which is low enough that the crudeness of the primitives never reads — only the outline does. Unlit matters: a lit ghost picks up shading and specular that give the primitives away.
  - Limbs hang off **empty pivots at the shoulders and hips**, because a primitive's own pivot is at its centre — rotating the capsule directly would spin it about its middle instead of swinging from the joint.
  - Only position and yaw are recorded, so the walk is **inferred from distance travelled** (`GhostReplayer.SwingLimbs`). Phase advances with distance rather than time, which keeps stride length constant instead of the legs spinning faster the quicker the ghost moves, and the amplitude scales with speed so a stationary ghost stands still rather than marching on the spot.
- `Interactables/FloorButton.cs` — hold-type; active if the real player OR any ghost is currently holding it. The player side is **polled in `FixedUpdate` (bounds overlap), deliberately not `OnTriggerEnter/Exit`**. `Teleport` disables and re-enables the CharacterController inside a single frame, so a player standing on the button when the iteration ended never generated the exit callback: the button stayed lit forever with nobody on it, and since `PlayerRecorder` samples `PlayerHolding`, every ghost recorded after that held it forever too. Don't "simplify" this back to trigger events.
- `Interactables/Door.cs` — slides the door panel by `openLocalOffset`, derived from an `openAmount` 0..1 rather than by a one-shot coroutine, so a door caught mid-slide can reverse without a special case. It owns **no** indicator state; the lamp is `DoorIndicator`'s, above. `SceneBuilder` sets that offset to +X, i.e. sideways into the wall pocket — the field's own default is still a vertical slide, so read the built value, not the declaration. `Close()` snaps it shut again and is called by the loop every iteration.
  - **The two doors open by different rules, and the difference is the puzzle.** Room2's key door **latches**: `KeyLock` calls `Open()` and it stays open, because putting a key in a lock is not something walking away undoes. Room1's door **tracks its pad** (`requiredFloorButton`) — step on, it opens across the room; step off, it shuts.
  - **Tracking rather than latching is load-bearing.** A door that latched open the instant the pad was touched is solvable in one iteration — step on the pad, stroll through — which deletes the premise the whole game rests on. Tracking is also what teaches the rule: the player watches the door open and shut with their own feet in the first seconds, and learns at that moment why one person cannot do both jobs at once.
  - **`DoorButton` is gone** (`Assets/Scripts/Interactables/DoorButton.cs`, in git). A play-test found testers could not locate it at all: they held the pad for an iteration, walked to the door in the next, and expected it to open. They were right to — the button was a second gesture the room never explained, and it bought the puzzle nothing, since either way the player spends one iteration on the pad and is at the door in the next. Removing it also makes the ghost's contribution **visible from anywhere in the room**: you are across the floor when a past self steps on, the plate clunks, the lamp goes green and the door slides open in front of you. That moment used to be followed by a walk over to press something. The wall beside the door is now bare, which is part of the point — there is no affordance left to mislead.
  - **The door refuses to shut on the player** (`doorwayClearance` 1.2m, tested against the *closed* slab's world position cached in `Awake`, since the door root sits at the room centre rather than at the opening). A `CharacterController` is not pushed by a moving transform, so a slab closing through one leaves the player inside it. The `openAmount > 0f` guard on that test is not a shortcut: without it, walking up to a shut door would hold it open forever. With it the reprieve only extends a door that is *already* open, and it cannot be used to reach one — the run from the pad to the doorway is **7.7m (1.7s at `moveSpeed` 4.5) against a 1.0s close**. Re-check that margin if either the pad moves or `openDuration` drops.
  - It also does double duty as anti-frustration: the intended solve no longer fails by half a second when a ghost's timing is a fraction short.
  - The open sound fires on the transition out of fully-shut, not from `Open()`. Closing is silent — that is the pad being released, which `FloorButton` already announces from wherever the player is standing.
- `Interactables/Drawer.cs`, `Interactables/CarryableItem.cs`, `Interactables/PlayerHand.cs` — the drawer, things you can pick up with E, and what you are carrying. All three poll range in `FixedUpdate` rather than using trigger callbacks, for the reason documented on `FloorButton`.
- `Interactables/Balloon.cs`, `Room/BalloonField.cs`, `Interactables/BalloonTool.cs` — one balloon, the pooled field, and swinging at them. `BalloonTool` uses an **overlap sphere, not a raycast**: in a room packed with balloons, having to line one up in the crosshair turns a physical act into a shooting gallery.
- `Interactables/KeyLock.cs` — Room2's door, and now **the only thing in the game that asks for a press to open a door**. It does not fire on arrival: walking into a locked door should not burn the attempt before the player has understood it is a lock.
- `Ghost/RecordedTimeline.cs` — frames plus pop events. `PlayerRecorder.EndRecording` returns one of these now, not a bare `List<RecordedFrame>`.
- `Room/PanelMessage.cs` — Room3's four wall displays and the one-shot announcement that goes with them. See the Room3 notes under **Scene layout**.
- `Room/WallPanelDisplay.cs` — owns every wall panel's colour: the boot sweep at the top of an iteration and the collapse flare at the end. See **Art assets** for the tuning. One thing not obvious from the name: `SceneBuilder` gathers its `panels` array from **the whole `Room/` tree, both rooms**, so Room2's panelling boots and flares in lockstep even though nobody is in there.
- `Loop/CarriedItemsDisplay.cs` — top-left readout of what the player is carrying, **as icons**. It exists because carrying is the one piece of state the loop rewinds that the player otherwise cannot see: the pin is visible in the hand, but the key is **pocketed** (`CarryableItem.showInHand` false, so taking it does not knock the pin out of the hand you needed to get it with), and without a readout "do I still have the key" is only answerable by walking to the door and trying it.
  - Icons rather than words for the same reason the HUD is monospace and the room is built out of displays — this is the facility's readout, not the game's subtitle. They also survive being glanced at, which is all this ever gets: it is read on the move with sixty seconds running.
  - A **fixed pool of four `Image` slots** built by `SceneBuilder`, enabled and disabled rather than created and destroyed, so a pickup costs no allocation mid-iteration. Rebuilt only when `PlayerHand.Version` changes.
  - `CarryableItem.displayName` survives the switch and now only names the slot object in the hierarchy — still worth having when four identical `Image`s are the alternative. `itemId` remains the wire value other scripts match on (`KeyLock` asks for `"Key"`).
- `Loop/ControlHintDisplay.cs` — a grey disc with an `E` on it floats over whatever interactable the player has walked up to, and a second disc carrying a mouse glyph appears on the pin the moment it is in hand.
  - **These used to retire permanently on first use, and play-testing overruled it.** The reasoning for retiring was real — the loop's whole texture is repetition, so an instruction replaying every sixty seconds becomes the most repeated thing in the prototype — but testers never found the door button at all, and the ones who did could not find it again an iteration later. **A prompt shown once has not been taught, and a control the player cannot find is worse than one they are reminded of.**
  - What survives of that reasoning is the restraint, and it is why the prompts do not read as clutter: the disc appears only when E would actually *do* something here (`WantsInteractHint`, not mere proximity), only over the nearest such thing, and at `maxAlpha` **0.75** rather than full — so it reads as a label stencilled on the fixture rather than as the game talking. If it ever does start to grate, that is the dial.
  - `IInteractHintTarget` is the abstraction — `WantsInteractHint` means "E right now would do something here", not "the player is standing near it". A shut drawer with the pin inside is one place with two answers, and prompting over the object that would *ignore* the press teaches the wrong thing. Implemented by `Drawer`, `CarryableItem` and `KeyLock`; the display picks the **nearest** one wanting it. Room1's door is not in the list any more, because it has no control to press.
  - `ControlHintDisplay.interactTargets` is typed `MonoBehaviour[]`, not `IInteractHintTarget[]`, because **Unity does not serialize interface fields** — the cast back happens once in `Awake`.
  - Positions come from `WorldToScreenPoint` into a full-screen rect via `RectTransformUtility.ScreenPointToLocalPointInRectangle` with a **null camera** (the canvas is ScreenSpaceOverlay; passing one skews the result). The `z <= 0` test is load-bearing: `WorldToScreenPoint` happily returns a mirrored on-screen position for anything behind the eye, so without it a prompt for something at your back appears in front of you.
  - Silent while `LoopManager.IterationRunning` is false, like everything else the facility does — the player has no control during the wake-up, so a prompt would be describing a button that does nothing.
- `Loop/PauseMenu.cs` — Escape's overlay, the settings screen, and the only thing in the project that touches `Time.timeScale`. See **Pausing** above; the part to know before adding anything is `LoopManager.AcceptsInput`.
- `Loop/GameSettings.cs` — the only persisted state in the project (one float, the mouse sensitivity). See **Mouse sensitivity** for why it has to be a setting rather than a constant.
- `Loop/EscapeTrigger.cs`, `Loop/EndingSequence.cs` — the way out and what happens when you take it. See **The ending**; the part to read before touching either is why the trigger sits on the threshold rather than past it.
- `Menu/MainMenu.cs` — the title screen's only script: `PLAY`, `QUIT`, and the async load. The progress bar shows the **lesser** of real progress and elapsed fraction of `minimumLoadingTime`, so the floor stops a fast machine flashing the whole load past in two frames without ever letting the bar claim more than has actually happened. Unity reports `0..0.9` while `allowSceneActivation` is withheld and never reaches 1, so it is rescaled — a bar that stops dead at 90% reads as a failed load.
- `Loop/CountdownTimer.cs`, `Loop/EndCycleControl.cs` — the two HUD readouts in the top-right. `EndCycleControl` is a real mechanic rather than a debug aid; the reasoning lives in **Scene layout**.
- `Audio/NarrationDirector.cs`, `Audio/RoomAmbience.cs` — the PA announcer and the room tone/machinery. See the **Audio** section for the cue schedule and why the clip slots are allowed to be null.

## Audio

The room has a diegetic PA announcer, taken from the reference film: every iteration is announced on a fixed schedule. That schedule is the whole system — four cue types per loop, plus one for a voluntary end.

| Cue | When | Method |
| --- | --- | --- |
| "Iteration N, 60 seconds remaining." | after the wake-up, as the clock starts — **no chime** | `NarrationDirector.AnnounceIteration` |
| "10 seconds remaining." | `LoopManager.tenSecondCueAt` (T-12, not T-10) | `AnnounceTenSeconds` |
| "Nine." … "One." | one per whole second, T-9 to T-1 | `AnnounceCountdown` |
| "New cycle initialized." | top of the next iteration, under the closed eyelids | `AnnounceNewCycle` |
| "Cycle terminated." | the player ends the cycle early | `AnnounceCycleTerminated` |
| "Containment failure. Cycle broken." | the player escapes — once per run, ever | `AnnounceCycleBroken` |
| "Manual termination available. Hold N to end the cycle." | first time the player reaches Room3 | `AnnounceManualTermination` |

- **The T-10 line is cued at T-12 on purpose.** It runs about two seconds, and from T-9 the digit countdown replaces whatever the announcer is saying every second, so cueing it at a literal T-10 clips it after one word. `tenSecondCueAt` is serialized — retune it if the line is ever re-recorded at a different length.
- Cues are **pushed from `LoopManager.RunLoop`, not polled** by the director. The loop already owns `ElapsedTime`, and the announcer has to stay silent through the wake-up, which sits outside the timed window. The counting loop guards on a *falling* whole second, so it fires exactly once per second at any frame rate.
- Iteration 1 gets no "New cycle initialized" and no reset sting — it opens the run rather than resetting it.
- **The ending line is chimed**, because it is the most important thing the facility ever says and the only announcement a run hears exactly once. Its wording is built out of vocabulary the player already has — cycles get *initialized* and *terminated* all game — so a cycle being **broken** lands as the same voice admitting the machine failed. Two sentences on purpose: the facility reacting, then the loop's own language closing.
- **The iteration line has no chime in front of it**, though the T-10 and "Cycle terminated." lines still do. It fires at the top of every iteration, so it is the one announcement a player hears hundreds of times, and a two-note ding ahead of it made the loop's most repeated moment its most decorated.
- **The number rises.** The iteration lines are generated from SSML rather than plain text so the number can be lifted in pitch and left climbing — "Iteration one!" rather than a label read off a list. See the generator notes for why that takes a question mark.
- **Announcements replace each other** (`Stop()` + `Play()`), never `PlayOneShot`. The countdown fires once a second and one-shots would leave the digits slurring over each other.

### The PA treatment

The announcer is not played dry — `SceneBuilder.AddTannoyFilters` puts the voice **and** the chime through a five-stage filter chain so they read as a horn on the wall of a hard, empty room rather than as narration over the top of the game.

- **It is a runtime chain on the `AudioSource`, not baked into the WAVs.** The clips stay clean masters, retuning is an Inspector drag rather than a regeneration, and a better-acted take dropped into `Assets/Audio/Voice/` inherits the whole treatment for free.
- **Component order on the GameObject *is* the signal chain** — Unity runs filters top to bottom, so they are added in processing order. Reverb goes last: ahead of the distortion it grits up the tail as well as the voice, which reads as a broken speaker rather than as a room.
- Band-limiting does most of the work, not the reverb. High-pass **340 Hz** / low-pass **3600 Hz** with the low-pass left slightly resonant (`Q` 1.6) — a horn driver has no bottom and no top, and that resonant peak is the nasal honk of every station announcement ever made. The ear identifies the *channel* long before it identifies the space.
- Distortion is **0.17**. Past ~0.3 the words stop being intelligible, and the announcer is carrying actual information (the iteration number).
- Echo **105 ms** at `decayRatio` 0.22 / `wetMix` 0.33 — roughly the round trip across a room this size, so it reads as *this* room. Reverb is `AudioReverbPreset.User`, `decayTime` 2.1s with `roomHF` -900 and `decayHFRatio` 0.55, i.e. a deliberately dark tail: hard painted panels absorb little low and plenty high, and a bright tail would undo the band-limiting.
- **`Tools/preview_pa_voice.py` renders the same chain offline** so it can be judged without launching the Editor (`python Tools/preview_pa_voice.py voice_count_3`). It is an approximation — Unity's reverb is FMOD's, this is a plain Schroeder network — so trust it for "how much echo" and "can I still make out the number", not for the exact tail. **Its constants mirror `AddTannoyFilters`; change one and change the other**, or it stops predicting anything.

### Where the audio comes from

- **Getting a rising ending out of SAPI requires a question mark**, and the iteration lines are written `Iteration <prosody pitch="+35%">N</prosody>? 60 seconds remaining.` on purpose. The terminal contour is chosen from sentence punctuation and overrides everything else — measured on Zira over the number at rate -2: `"1!"` 220→160 Hz (falls; the exclamation does nothing), `prosody contour="…"` 202→138 Hz (SAPI ignores the attribute), `"1?"` 182→232 Hz, and `pitch +35%` **plus** `?` 179→259 Hz. The `?` is never spoken, and because it closes the sentence on the number the rise sits there — leaving it to the end of the whole line instead would turn "remaining" into a question.
- **Rate is -2 for the sentences, -1 for the countdown digits.** The synthesizer's default clip is what made it read as a screen reader rather than a PA. The digits cannot go slower than -1, since each has to finish inside its one-second slot before the next replaces it — verified: the spoken part of every digit ends by 0.78s, and the trailing silence in the file is irrelevant because `Speak` stops the previous clip.
- **Narration is generated, not sourced.** `Tools/generate_narration.ps1` drives the Windows built-in synthesizer (`Microsoft Zira Desktop`, en-US female) to write all 45 lines into `Assets/Audio/Voice/` (30 numbered iteration lines + a generic stand-in, 9 countdown digits, the T-10 line, "New cycle initialized.", "Cycle terminated.", "Containment failure. Cycle broken." and the Room3 manual-termination line) as 22 kHz 16-bit mono WAV. It costs nothing, runs offline, and keeps the voice track in the same "reproducible from a script" category as the rest of the project. The flat synthetic delivery happens to suit a facility tannoy. To replace them with better-acted takes, keep the filenames — no C# refers to how they were made. `SceneBuilder.NarrationIterationLines` must match the range the script writes (currently 30, then a generic line stands in).
- **SFX are generated too**, by `Tools/generate_sfx.py` — twelve clips (floor-button press and release, door, gasp, sheet rustle, room-tone loop, pull-in, power-down, chime, balloon pop, drawer, item pickup), synthesised from scratch with the Python standard library, no numpy and no downloads. Each is seeded, so re-running the script reproduces the identical set. See `Assets/Audio/SFX/README.md` for the filename table.
  - **`sfx_balloon_pop` is kept under a fifth of a second on purpose**: seventy of them can be in flight at once, and anything with a tail turns a roomful of balloons into a wash. Each balloon also carries a **fixed detune** (`audioSource.pitch`, from the field's seed) — one clip across seventy balloons reads as a machine gun, and a balloon keeping the same voice every iteration is one more thing about the room that stays put.
  - **There is no tool-swing sound yet.** `BalloonTool.swingClip` is deliberately left null rather than borrowing the bed's sheet rustle; swinging at air currently gives no audible feedback, which is a known gap.
  - This is the same bargain the narration and the wall grain make: everything in the project has to rebuild from a script, and a folder of sourced CC0 clips was the one part that could not. They sound synthetic, which a tannoy-equipped facility gets away with.
  - **The room-tone loop is the one with a real constraint on it.** `RoomAmbience` plays it on `loop`, so a seam is a click every 8 seconds for the whole session. Every partial in it is a multiple of 1/8 Hz so the tone wraps exactly, and the noise layer is wrapped by crossfading its own tail back over its head (`seamless()`). Verified numerically: the sample step across the wrap is smaller than the largest step inside the clip, i.e. no discontinuity.
  - `SceneBuilder.BuildAudio` resolves each one via `LoadClip`, which is extension-agnostic (`.wav/.ogg/.mp3/.aif/.aiff`). **A missing file resolves to `null` and every player guards on it**, so an emptied SFX folder is still a valid, playable state. Overwriting a generated clip with a recorded take under the same name is the entire swap.
- Unity MCP's `generate_audio` is **not** an option for the voice: it does music/SFX only, no speech. It also needs a fal.ai key that is not configured on this machine.

### Sources and spatialisation

`SceneBuilder.MakeSource` builds every `AudioSource` with linear rolloff (`maxDistance` 14) rather than Unity's logarithmic default, which stays near full volume across a room this small.

- **2D** (`spatialBlend` 0): the PA voice and chime (a room-wide tannoy has no position to walk away from), the music bed, the machines, and the player's own breath.
- **3D**: the door and the floor button.
- **There are no footsteps.** A `FootstepPlayer` existed (distance-paced, like `GhostReplayer.SwingLimbs`) and was removed along with its four clips — in a room this small, with a 60-second clock, the player's own steps were noise over the announcer rather than presence. Git has it if it's ever wanted back.
- **The floor button is audible, and it is audible for ghosts too.** `FloorButton` fires a clunk on the *edges* of `IsActive`, whoever caused it — the pad is a physical plate, and it does the same thing under a ghost as under the player. This is a real affordance rather than dressing: `DoorIndicator` only reports the condition to a player who happens to be looking at the door, whereas the clunk reaches you facing the other way. A hold that ticked while held would be unbearable across a full iteration, hence edges only.
  - **Silent while `LoopManager.IterationRunning` is false**, for the same reason `Door.Close()` is silent: the loop releases every ghost during the reset, and a rack of pads letting go behind the closed eyelids is the machinery showing through rather than a sound the room makes.
- **The loop boundary is two sounds split across the blackout**, not one cue at the top of the next iteration as it used to be. `PlayPullIn` fires the moment the iteration ends — while the lids are still falling and the panels are still flaring — because that is the moment the loop takes you; held until after the blackout it becomes an explanation of something that already happened. `PlayPowerDown` then lands under the black, with nothing to look at while the room goes out. The panels booting during the wake-up are the third beat: **taken, switched off, switched back on.**
  - Both fire at the *end* of an iteration, so unlike "New cycle initialized." they need no `IterationNumber > 1` guard — there is always an iteration before them.
  - `sfx_pull_in` runs two motions against each other: a noise band climbing while a tone falls away underneath. Up and down at once reads as being pulled *through* something; either alone is just a riser or just a drop. It ends on a hard cut with the sub arriving a beat late, rather than decaying.
  - **A third cue, `sfx_glass_rattle`, was removed** — high-Q pings off the nightstand props, which at the loop boundary read as a doorbell going off every 60 seconds.
- `Door.Close()` is **deliberately silent** — that's the loop rewinding world state behind a black screen, not the door being shut. A sound there draws attention to the seam.
- Exactly **one `AudioListener`** exists, on the player camera. Adding a second is a Unity warning and breaks positional audio.

## QA findings

A full QA pass on 2026-08-09 (build verification + code review + scene-file inspection + spec conformance). Fixed:

1. **The closed door had no collider.** `SceneBuilder` built `DoorPanel` with `removeCollider: true`, and `BuildPanelWall` cuts the doorway out of *both* walls' collision — so the two rooms were permanently connected and the player could walk straight through the closed door, bypassing the puzzle entirely and violating spec §2's "단일 iteration만으로는 절대 풀 수 없다". Invisible while Room2 was still a dead-end recess. The slab now keeps its collider; once open it sits at x 0.65..1.95, entirely behind the wall's own collision, so it never blocks the opening it just cleared.
2. **The door was world state the loop never rewound.** `Door.IsOpen` stayed true forever and `Open()` early-outs on it, so every iteration after the first solve began with the door already open. `Door.Close()` now snaps it back, called from `RunLoop` *after* the teleport so a player standing in the doorway is already back at the bed.
3. **`DoorButton.playerInRange` got stuck true**, the same defect already documented on `FloorButton`: `Teleport` disables and re-enables the CharacterController inside one frame, so `OnTriggerExit` never arrives. Standing at the button when an iteration ended left `E` opening the door from anywhere in the room, including from the bed. Now polled in `FixedUpdate` via bounds overlap, pressing on the rising edge.

A follow-up pass then fixed four more:

4. **The floor button's activation zone was far larger than it looked.** Its trigger was `radius 0.5, height 0.5` — height under 2×radius, so Unity silently clamped it to a *sphere* — and `FloorButton` tested AABB overlap, which adds the player's own 0.3 radius, giving a ±0.8m square around a visible disc of radius 0.35. You could stand half a metre clear of it and it lit. **It has no collider at all now**: the pad is a logical volume testing the player's centre against `activationRadius`, which `SceneBuilder` derives from the visual radius so the two can't drift, plus a foot-height check so jumping off it releases.
5. **Control and recording stayed live through `CloseEyes()`** — ~1.6s of blind walking, and since `ElapsedTime` is frozen at `loopDuration` by then, every one of those frames recorded at the same timestamp and the ghost skipped the lot in one jump on its final tick. Both now stop before the eyelids start closing.
6. **`EditorBuildSettings.m_Scenes` was empty** — a standalone build would have shipped no scenes. `Build()` now reasserts it every run, since the list lives in ProjectSettings and nothing else maintains it.
7. **`CanvasScaler` was on the default `ConstantPixelSize`**, pinning UI text to a fixed point size. Now `ScaleWithScreenSize` against a 1920×1080 reference.
8. **The generated scene was tracked in git.** Unity re-randomises the fileID of all ~1,700 objects on every rebuild, so a one-line script change produced an 11,000-line scene diff with no semantic content, and any merge of two rebuilds was a guaranteed conflict over noise. `Assets/Scenes/*.unity` is now ignored — `SceneBuilder` is the source of truth, so the scene is build output. **The `.meta` is deliberately still tracked**: it pins the scene's GUID, which `ProjectSettings/EditorBuildSettings.asset` stores by value, so dropping it would make every clone regenerate a different GUID and dirty that file.

Still open (found, not fixed):

- Spec deviations: the floor button sits on the bed's left where spec §3 says right (it follows `room_layout_sample.png` instead); the ghost reset of spec §4.6 is not implemented at all. (Spec §5's door button no longer exists — see `Door` — so its "아무 반응 없음" denial deviation is moot.)

## Art assets

- `Assets/ArtAssets/Furniture/` holds exactly what the scene uses: `messy_bed.glb` and `nightstand.glb`. **Both are Creative Commons** (confirmed by the user, 2026-08-10, when the first distributable build was being prepared) — if the exact variant is BY rather than 0, the build needs an attribution line, so record the source URL here the next time either is touched. Five bed models were placed side by side and compared in-engine; `messy_bed` won because its bedding is rumpled and slept-in — the loop opens every iteration by waking up here, so a neatly-made bed undercuts the whole premise. Cost of that choice: **306,907 triangles**, 20-60x the alternatives (fine for one object, worth knowing before adding more). The four rejects were deleted afterwards (~78MB); if a different bed is ever wanted, they have to be re-downloaded.
  - **`.glb` needs `com.unity.cloud.gltfast`** (6.19.0, installed). Without it Unity imports a `.glb` as an opaque `DefaultAsset` and it can't be instantiated at all.
  - Keep the glTF materials these ship with; a hand-rolled URP/Lit stand-in drops the metallic/roughness maps.
  - **These models bake contact shadows into their occlusion maps**, which only looks right in the exact pose they were authored in. Moving the pillow and hiding its neighbour left those shadows painted on the bedding — a dark smear beside the pillow and a hard black band across the pillow itself, which read as dirt rather than shading. `DisableBakedOcclusion` fixes it by cloning the material into a project asset with `occlusionTexture_strength = 0` (applied to `Sheet` and `Pillow_2`); the scene's SSAO then supplies contact shadows that follow the actual geometry. The clone has to be its own asset because the glb's materials are sub-assets that get regenerated on every reimport. If furniture ever shows a shadow that doesn't move with the light, this is the cause.
  - **All five are authored Z-up**, so every one needs `rotation: Quaternion.Euler(-90, …)` to stand up — but their **units differ wildly**, and their bounds are not centred on the origin. Don't assume centimetres: `old_bed` is already in metres, `lowpoly_bed` sits 2.8m off-origin. The reliable way to place a new one is to measure its bounds at scale 1 and derive `uniformScale = 2.05f / max(horizontal extent)`, which is how `messy_bed`'s 0.00941 was found. `PlaceModel` then handles centring and floor-seating.
- `SceneBuilder.PlaceModel(...)` instantiates these via `PrefabUtility.InstantiatePrefab` and repositions them so their *rendered bounds* (not their raw mesh pivot, which is at an arbitrary corner) are centered on a target X/Z with their base resting on a given floor Y. Reuse this helper for any future model placement instead of hand-computing offsets. It takes an optional `rotation`, applied **before** bounds are measured, so a model authored Z-up or facing the wrong way still lands centred and on the floor; the generated `BoxCollider` un-rotates the world-axis-aligned bounds back into local axes so a rotated model doesn't get its height and depth swapped.
- Room shell stays procedural — walls are generated panel geometry (`BuildPanelWall`), floor and ceiling are plain white slabs sharing one material (`FloorWhite`, matte at 0.18, with the same plaster grain normal as the walls but at a far higher repeat count since a slab face is 9 x 10.9m against a wall panel's 1.7 x 0.9m). **Albedo is flat colour everywhere and should stay that way**: the reference room is plain white panels, so realism comes from geometry and lighting, not from painted-on detail.
  - A **marble floor was built and then dropped** — the veining, however faint, pulled the room from "cell" toward "hotel lobby". Worth knowing if it comes up again: turbulence marble needs `turbulenceScale` above **one full cycle** (0.55 only wobbled the sine bands half a cycle, so they stayed parallel and read as wood grain or ripples; 2.2 made neighbouring bands cross and merge into something stone-like). Also, a textured floor **cannot carry the grain normal map as well** — URP/Lit drives every secondary map from `_BaseMap`'s single UV transform, so the normal would be forced to the albedo's tiling and the grain would come out metres across.
- **The HUD's glyphs are drawn from code too** — `Assets/Textures/Icons/` (`icon_pin`, `icon_key`, `icon_hint_disc`, `icon_mouse_left`), written by `SceneBuilder.IconCanvas`, a ~60-line software rasteriser. Shapes are predicates over a 0..1 square, composed with `&&` and cut back out with a `sign` of -1, at **4x4 supersampling** — which is the only reason a 128px disc has a clean edge instead of a staircase. Three notes:
  - The origin is **bottom-left**, matching Unity's texture coordinates, so a row index needs no flipping.
  - They are **white with the shape entirely in alpha**, because the HUD tints them through `Image.color`; a glyph with baked-in colour could not be recoloured to match the red.
  - They import **uncompressed** — block compression frays the edge of something that is nothing but alpha, and these are a few KB each.
  - The pin's needle is drawn deliberately **fatter than the real pin is**: authored at 128px and displayed at 58, a true needle lands on one screen pixel and vanishes.
- **Surface relief is a generated normal map**, `Assets/Textures/SurfaceGrain.png`, written by `SceneBuilder.MakeNoiseNormalMap` — no sourced texture assets, so the project stays reproducible from scripts. Multi-octave value noise made **tileable by wrapping the lattice** at each octave's period (`LatticeHash`); `Mathf.PerlinNoise` is not tileable and would seam at every repeat.
  - Applied via `ApplySurfaceDetail`. **`_BumpScale` is much larger than the sub-1 that looks like a sane default.** Central differences across a smooth multi-octave field give very small gradients, so the map is genuinely shallow: at 0.7 the surface rendered *perfectly flat* even with the camera against it, and at 10 it turns to stucco. The **floor** uses 1.8 (reads as painted plaster up close, vanishes at room distance). The **walls** are deliberately down at **0.2** — see the gloss note below.
  - **Walls are a smooth glazed panel, not plaster**: `_Smoothness` **0.85**, relief kept to a whisper (0.2) purely so the specular isn't a perfectly uniform sheet, which is what makes a flat surface look CG. The floor stays matte by comparison (0.18), as a hard-wearing floor finish would be against a glazed wall.
  - **The wall panels are displays, and they boot at the start of every iteration** (`WallPanelDisplay`, driven from `WakeUpSequence`): dark (`WallPanelColor`, 0.13) when you wake, sweeping to white as you sit up. This is the visual half of the announcer's "New cycle initialized" — the facility powering the cell back up — and it retroactively makes the wall grid *diegetic*: the panels aren't tiles, they're screens, which is why the room is built out of them.
    - Panels come up **from the floor rows first, with per-panel scatter** (`onsetJitter`). A uniform fade reads as someone turning a dimmer; a staggered one reads as separate screens waking. Onsets are computed once in `Awake` from world Y, with a **fixed random seed** so the boot looks identical every iteration — a loop should.
    - Driven through a **`MaterialPropertyBlock` on `_BaseColor`**, not by touching the shared material, which is what allows the panels to differ mid-sweep. Note this breaks SRP batching across the 182 panels; fine at this scale, worth knowing if the room ever gets much bigger. (`_Color` would silently do nothing here — URP/Lit's albedo is `_BaseColor`.)
    - `PowerDown()` is called with the eyelids already shut, so the reset is never seen: the player only ever witnesses the room coming *back*, never it going out.
    - **The last `LoopManager.collapseLeadTime` (10s) of a cycle is a collapse**: `SetFlare` blows the panels out past white with heavy emission while `CameraShaker` ramps up, both building to the moment the loop takes you, and both held at full through the blink shut before being cleared behind the black. The ramp is **squared** — a linear one reads as a slider being dragged. `PanelWhite` has `_EMISSION` enabled with a black colour purely so the keyword is compiled in for this; a property block cannot turn a shader keyword on.
      - **Escaping is the one case where it does not peak.** `LoopManager.RunEnding` ramps it back down from wherever it had got to (`WallPanelDisplay.Flare`), so a player who gets out in the last ten seconds watches the collapse fail rather than complete. See **The ending**.
    - The material itself stays **white**, because that is the resting state for all but the first seconds of an iteration and it is what the reflection probes bake against.
  - **Gloss only works because of the reflection probes** (below). Raising smoothness without them paints the blue procedural sky over every white panel — that is the exact failure the old "0.03 smoothness everywhere" rule existed to dodge, and it is why `reflectionIntensity` used to be crushed to 0.1.
  - Note that **a mirror of a white room is still white.** The gloss reads as sheen and a smooth falloff rather than as visible reflected objects, because there is almost nothing in the room with contrast to reflect. If a harder "switched-off display" look is ever wanted, the panels need a *darker* albedo — the reflection is already there.
- **One baked reflection probe per room**, three of them (`SceneBuilder.BuildReflectionProbe`), box-projected and sized to the room so a reflected wall stays on the wall instead of sliding as the camera moves. `RenderSettings.reflectionIntensity` is back up to **1.0**.
  - **Baked, and baked during `Build()`** via `Lightmapping.BakeReflectionProbe`, writing `Assets/Textures/Room*_Reflection.exr`. A Realtime probe was tried first, reasoning that the rebuild-from-scratch workflow would invalidate baked data — but **a realtime probe renders nothing until play mode**, so `probe.texture` came back EMPTY and the glossy walls had nothing to reflect at all. Baking in the build gets both: a real asset, regenerated in lockstep with the geometry it captures, for two small cubemaps' worth of build time.
  - Probe `resolution` is **512**: at 256 the ceiling fixtures reflect as vague smears rather than panels.
  - **Tiling must be set on `_BaseMap`, not `_BumpMap`.** URP/Lit drives the normal map's UVs from `_BaseMap`'s transform, so a scale on `_BumpMap` does nothing at all. Tiling is per face, and a wall panel's face is ~1.7 x 0.9m against a floor slab's 9 x 10.9m, hence the very different repeat counts (5,3) vs (26,30) for the same ~0.35m grain.
  - Smoothness went from 0.03 to **0.14–0.16**. At 0.03 there is almost no specular response, so the relief only shows in diffuse shading and barely reads at all — still well short of the 0.5 default that mirrors the skybox onto the walls.
  - Note the map imports with `TextureImporterType.NormalMap`; without that the shader reads raw RGB as a normal and tilts every surface. It also means you **cannot measure it by sampling `.r`/`.g`** — Unity re-encodes to DXT5nm, so red comes back as 0 or 1 everywhere and any "deviation from flat" measurement is meaningless. Judge it from a render.
- **Furniture is the remaining gap.** The Kenney models are deliberately low-poly with flat per-face colours, so no texture work makes them look real — they have to be replaced with better models. Recommended CC0 sources: Sketchfab's CC0 filter (best furniture selection), Poly Haven (props/textures/HDRIs), ambientCG (textures). Claude can't download these, so the user drops them in `Assets/ArtAssets/Furniture/` and `SceneBuilder.PlaceModel` handles placement.
- Ghost material is `GhostFaint.mat` — URP Unlit, transparent, near-black at alpha 0.16, so it reads as a faint afterimage rather than a solid lit shape. The URP transparent set-up needs all of `_Surface`/`_SrcBlend`/`_DstBlend`/`_ZWrite` **and** the `_SURFACE_TYPE_TRANSPARENT` keyword; set the colour alone and the shader stays opaque, rendering a solid black mannequin.

## Gotchas already hit (don't rediscover these)

- A fresh Unity project via `-createProject` does **not** include `UnityEngine.UI` (uGUI) by default — needed `"com.unity.ugui": "2.0.0"` added to `Packages/manifest.json` before any `Text`/`Canvas` script compiles.
- Unity Hub's folder-picker "프로젝트를 찾을 수 없습니다" error on this machine is a Hub UI issue, not a project problem — launch `Unity.exe -projectPath ...` directly instead.
- **A world-space Canvas is legible when its forward (+Z) matches the direction the viewer is LOOKING — not when it points at the viewer.** Unity's own default scene is the proof: camera at z = -10 looking toward +Z, canvas at the origin unrotated, text the right way round. So a message on a wall must face the *same* way as the eyes reading it, i.e. **away from the room, into its wall**. Getting this backwards renders the text mirrored, which is what happened to all four of Room3's wall messages on the first build — and note that "face the normal inwards" is the intuition to distrust here, since it is also what you would do for a physical sign.
- **A `RectTransform`'s serialized `m_LocalPosition` is stale, and reading it will convince you a correct build is broken.** Its x and y come from `m_AnchoredPosition`, which Unity recomputes `m_LocalPosition` from on load — Room3's four wall messages all serialize as `m_LocalPosition: {0,0,0}` while sitting exactly where they should. **Inspect `m_AnchoredPosition`.** Related: `AddComponent<Canvas>()` (or any UI component) *replaces* a GameObject's plain `Transform` with a `RectTransform`, so a position written before that call is discarded — set the transform after.
- **There is no scripting API that creates a layer.** `SceneBuilder.EnsureLayer` edits `ProjectSettings/TagManager.asset` through a `SerializedObject`, which means the build has a side effect **outside the scene** — expect that file in a diff after a fresh clone's first build. It is idempotent by name, so rebuilds reuse the slot rather than burning one of the 24 user layers each time. Indices **0-7 are Unity's own**; three of them look blank and are not, and writing into one is silently dropped, so the search starts at 8.
- **`-nographics` cannot render anything**, which is why the menu background capture is conditional on `SystemInfo.graphicsDeviceType`. Anything else added to the build that needs a real render has to make the same check, or the canonical headless build stops working.
- A batchmode build **fails outright if the Editor has the project open** ("another Unity instance is running"). When that happens, drive the same build through Unity MCP instead — `execute_menu_item("Iteration Room/Build Whitebox Scene")` — and read the result with `read_console`. Clear the console first: stale entries from before a rebuild look exactly like fresh failures.
