# Architecture and script index

What each script owns. Responsibility boundaries are load-bearing — the summary table and the rule
against merging roles are in CLAUDE.md §2.

---

## Script index (`Assets/Scripts/`, namespace `IterationRoom`)

Only what is not covered above.

- `Player/FirstPersonController.cs` — CharacterController movement, mouse look, jump. Also owns the pointer lock and the click-to-retry (browsers only grant capture inside a user gesture, so the lock requested in `Start` is routinely refused on WebGL). **Looking is skipped entirely while the cursor is loose**, or a pointer travelling across the page swings the view across the room.
- `Player/CameraShaker.cs` — sits on a **`CameraRig` between the player and the camera**, and that placement is the point: `FirstPersonController` rewrites the camera's own `localPosition` and euler angles every frame, so a shake applied to the camera itself is wiped instantly. Uses Perlin rather than `Random` — continuous noise reads as a building judder, per-frame random values as a broken frame rate.
- `Interactables/FloorButton.cs` — hold-type, active if the player OR any ghost is on it. The player side is **polled in `FixedUpdate`, deliberately not `OnTriggerEnter/Exit`**: `Teleport` disables and re-enables the CharacterController inside one frame, so a player standing on it when the iteration ended never generated the exit callback — the pad stayed lit forever and every ghost recorded afterwards held it forever too. **Don't "simplify" this back to trigger events.** `Drawer`, `CarryableItem`, `PlayerHand`, `KeyLock` and `EscapeTrigger` all poll for the same reason.
  - The pad has **no collider at all** — a logical volume testing the player's centre against `activationRadius` (derived from the visual radius so the two can't drift), plus a foot-height check so jumping off releases. Its old trigger was `radius 0.5, height 0.5`, which Unity silently clamped to a *sphere*, and an AABB test added the player's own 0.3 radius: a ±0.8m square around a disc of radius 0.35.
- `Interactables/SocketInsert.cs` — the shared slide-and-settle an object makes on its way into a socket, used by `SymbolSlot` and `FinalSlot`. **The object is already seated before the coroutine runs**: `InsertInto` has taken custody, so only where it is *drawn* is still moving — which is what makes the animation safe to interrupt, and why losing the socket (`transform.parent`) is the only stop condition it needs. It starts at the mouth rather than at the hand it came from because `InsertInto` restores the object's full size, and the slide would otherwise begin wherever the player's head happened to be. Each caller states its own `offered` offset: "out of the hole" is +Z for a recess in a wall and +Y for a well in a console top. **`KeyLock` is deliberately not rewritten onto this** — its move is a sequence (in, settle, turn, then the door), and folding that in would make the helper about the lock.
- `Interactables/PlayerHand.cs` (put-down placement) — where a released object lands is two questions, not one. **Room**: a spherecast of the object's own half-width forward from waist height, clamped to what it finds — and `minDropAhead` is what to use when the way is CLEAR, never a floor under the cast. Written as `Max(allowed, minDropAhead)` it silently undid the clearance it had just measured, and play found that as an escape object half-buried in Room4's console. **An object inside a structure is worse than one underfoot**: you can step off one and cannot dig the other out. **Sight**: clearing the geometry is not the same as being visible — a console hides its own foot from a 1.6m eye — so the point is walked back toward the player until the line from the camera to it is unobstructed. Closer is always more visible, because whatever is hiding it is in front.
- `Player/GameInput.cs` — **every verb this game has, asked once**: move, look, interact, use, jump, sprint, crouch, pause. Seventeen files polled `Input` directly (eight of them for the same E press), so a second input device meant editing every fixture in the building and getting all of them right. **Sampled lazily, once per frame** — every fixture polls E in its own `Update` and script execution order is arbitrary, so a touch flag raised part-way through a frame would be seen by the fixtures that ran after it and missed by the rest. That is the same coin-toss `PlayerLookup.ClaimInteract` exists to stop, one level lower. With no touch layer registered, every property is the expression that used to be written at the call site, so desktop is untouched.
- `Player/TouchControls.cs` — the screen read as a controller: a stick that appears under the thumb, drag-to-look anywhere not spoken for, and round buttons for E / USE / JUMP / pause. **Raw touches, not uGUI buttons**, for the frame-ordering reason above; the visuals are therefore non-interactive images placed at runtime from the same numbers the hit test uses, so a mark and the press it describes cannot end up in two places. **Sprint is the stick pushed past a threshold** rather than a button — a run is "more of the same input", so it costs no screen space — with hysteresis, because a single threshold under a resting thumb flickers. **No crouch**: it is the one verb the game never requires. **No end-iteration button either** — `EndCycleControl` is already a uGUI element with its own pointer handlers, so it needed nothing; what it did need is `OverInteractiveUI`, or the same thumb would have turned the camera while ending the iteration.
- `Player/HeldItemClearance.cs` — stops a held object reaching through a wall. The hold anchor sits *at* the camera and the item's offset lives inside it, so **moving the anchor** pulls the item in along the line it already sat on, so it stops at the surface instead of passing through it. It used to SCALE the anchor instead — which moves and shrinks by one factor, leaving apparent size unchanged — and that went with the shrink-to-fit hold: objects are held at their real size now, and a clearance that quietly resized them would be the same lie by another route. A big object pressed against a wall therefore comes toward the camera and takes more of the screen, which is what a big object against a wall does. The alternative — a second camera on its own layer drawn over everything — costs a camera, a layer and a renderer feature, and this project reconciles its renderer rather than appending to it. **The only cast in the project**, and both its exclusions are real: the player's own capsule, which the sphere starts inside, and the balloon layer, which the controller already ignores.
- `Interactables/FallingItem.cs` — on EVERY carryable: the fall when nothing holds it up, whether that is a support picked up out from under it or the player simply letting go at hand height. One axis, real gravity, to one known height — **not a Rigidbody**, for the reason carryables have never had one: the loop must put every object back exactly, and a simulated fall settles differently every time (the same argument behind `CarryableItem.DropAt` placing rather than dropping). **Nothing falls off its own shelf**: `CarryableItem.Released` is set by `DropAt` and by nothing else, and a component with no `support` stays inert until it sees it. Being above `RestingY` is not the same fact as having been let go of, and the first version treated them as one — which dropped the pin out of its drawer and the escape objects off their plinths the moment the scene loaded. A drop also travels: `Release` starts the object at the hand, where the player can see it, and glides it forward and turns it upright as it descends, with progress measured off the descent so both halves arrive together. Falls **only downward** — a support put back underneath does not lift it again; rebuilding the tower belongs to the loop's rewind, which sets the position outright. Nothing about the fall is recorded because it is derived: a ghost repeating the pickup causes it again. **The height it falls TO is `CarryableItem.RestingY`, not `floorY`** — `floorY` is the object’s own half-thickness above its own floor and `floorBaseY` says which floor, because cycles put a second storey under the first and one number cannot mean both without an object on the lower floor falling through it.
- `Interactables/PressPlate.cs` — a plate the player presses with E **outside the loop**. One subclass now: `Room/CalibrationStartButton.cs`, before the first iteration, which cannot gate on `LoopManager.AcceptsInput` because it is false for exactly the moment the plate has to work. Room4's plate used to be the other; it is gone, and the base is kept because the reason for it — a fixture that lives outside the iteration — is a real category with one member rather than an abstraction over one case.
- `Room/RewardPlinth.cs` — Room3 and the cube room's payout: a plinth carrying the yellow triangle that rises on **exactly the condition that opens Room3's door**, `FloorButton.AllActive(pads)`, asked here and by `Door` and `DoorIndicator` so a room cannot have two answers to one question. It rises and falls with the pads rather than latching, and what protects the player is that taking the triangle is a *pickup* — once it is in hand the plinth can sink under them. The triangle is **hidden**, not merely out of reach, while the plinth is down: `IsFreeForGhost` reads `visible`, so hiding is what stops a past self reaching through the floor at a timestamp when the pads happened to be held. Unlike `Door` it does **not** freeze while the loop is stopped — see the note in the file.
- `Room/CubeRoom.cs` — Room2East's rule: which cube belongs in which recess, whether they are all home, and the reward's request. One `IItemSocket` per **cube**, exactly as `ChessBoard` does per piece, which is the whole of how ghosts place them. Owns nothing visual.
- `Room/Bucket.cs` — one pail: how full it is, and emptying it. Filling is a **level derived** from where it is standing and whether the tap above it is on — nothing about it is recorded, exactly as `FallingItem` derives a fall from a release. Pouring is the opposite and is an **event**, spread over a second and a half: the bucket tips over its own lip (`PourPivot`, placed at the rim, with everything the bucket is made of hanging under it so the water inside goes over with the pail) while a stream falls from the lip to the tank's own waterline and the tank rises as it drains. The stream is placed in **world space** every frame because both its ends move — the lip rides a hand, the surface it lands on is rising.
- `Room/BucketStand.cs` — the named spot under a tap where a bucket catches the water, and **an `IItemSocket`**, which is what makes room2-2 solvable: a past self's "I put the bucket down here" is a `Surrender`, and a surrender replays by asking `ItemRegistry` for the socket it named. It is the first socket in the game that is not final — a bucket is put here in order to be taken away again — so `Release` is the way back out and `Update` notices every route that skips it. It also settles which tap is filling, because a bucket that searched for one would find one through a wall.
- `Room/WaterTank.cs` — room2-2's rule: a column that takes four bucketloads against a minute that holds fewer trips than that, which is the first thing in this game one iteration cannot do. Nothing is stored across the boundary; what accumulates is HANDS.
- `Room/PourPoint.cs` — where a pour is **recorded**, on the tank. It exists because pouring is the one thing a past self does in that room that hands nothing over: no custody changes, so no `CarryEvent` describes it, and without a signal bit of its own the tank could only ever be filled by the living player. A stretched pulse like every press, re-evaluated at the ghost's end against the condition that enabled it — a bucket with water in it, in that hand, now.
- `Room/BucketPlacer.cs` — the left button and the aim for a bucket, beside `ChessPlacer` and `BalloonTool` and unable to clash with either (each is silent unless the hand holds the one thing it acts on). Targets are aimed at through their **`Aim` anchors, not their transforms** — both the stand and the tank have their origins on the floor, so at conversational range the only point that counted was below the bottom of the screen.
- `Room/WaterFlow.cs` — one tap's water, split from the tap because the two halves have different lifetimes: the stream stops with the valve, the puddle it left does not. Also owns the **catch** — a bucket under the spout shortens the fall to its rim and takes the floor's share of the effect (the spill, the spray) with it, because those are what happens when water reaches a floor.
- `Room/WaterRipples.cs` — the rings the player leaves in that pool: a fixed pool of face-up quads with a generated ripple texture, expanded on a slowing curve and faded through a `MaterialPropertyBlock`. Drawn rather than shaded because the surface shader's noise is the same everywhere and answers to nothing — a ripple has to start where the player is — and pooled rather than instantiated so a player running in circles has a hard cap on how much transparent overdraw they can ask for.
- `Room/PanelDigits.cs` — the number on room2-7's scale, painted into a texture on the MODEL'S OWN display panel. Nothing is added to the scene: two earlier versions put something over the panel - a world-space `Canvas`, then a grid of quads - and both are the same mistake, a thing stuck on the prop rather than the prop showing something. It needed the submesh's UVs rebuilt first (`SceneBuilder.FlatUvMesh`), because the glb maps that patch into a 0.06-wide atlas window in which **U does not run across the panel** — see `gotchas.md`. Seven-segment bars drawn with `SetPixels32`, repainted only when the displayed value changes.
- `Room/Weighable.cs` — what one object weighs, on the object. A whole component for one float, deliberately: the alternative is a table inside `WeighScale` keyed by `itemId`, which puts a fact about an AXE inside the room that happens to contain a scale. The bucket is the one whose weight is not a constant — it reads its own `Level`, so an empty pail and a full one are the same carryable at 1.8kg and 12.0kg.
- `Room/WeighScale.cs` — room2-7's rule: a platform scale that sums whatever is standing on it (the player included, at 71kg) and latches when the reading hits its target. **Polled with an overlap**, because objects arrive here by being teleported home, by a ghost releasing them and by `FallingItem` scripting a drop — half of which never produce the enter/exit pairs a trigger needs. **Carried things do not count**: an object in a hand is being held up, not weighed. **It latches**, unlike a pad — the player's own weight is part of what it can read, so a target that included them would be one they could not walk away from.
- `Room/Valve.cs` — one wheel valve on room2-6's wall: press E, it turns one full turn, and after `turnsToOpen` (two) there is nothing left for E to do here. `LightSwitch`'s shape - the press is an EVENT, so the recorded signal is a stretched pulse on the rising edge and a ghost replaying it turns the wheel exactly once, with the condition (`Turns < turnsToOpen`) re-evaluated at the far end rather than replayed blind. The wheel is spun as an ANGLE rather than toward a destination: slerping to a 360-degree target is a no-op, since the shortest arc between a rotation and itself is nothing.
- `Room/PoolDrain.cs` — room2-6's rule, and the only place that says what the valves, the water and the door have to do with each other: six turns opens the cover, the open drain empties the pool, and the EMPTY pool is what the door hangs on. A `RoomCondition`, so `Door` asks it what it asks the tank and `Cycle.ResetRooms` rewinds it with every other room rule - and its reset stops the drain coroutine first, or a drain caught halfway across the boundary goes on writing a falling level into a pool that has just been refilled.
- `Room/WaterPool.cs` — room2-5's landing room is full of water, and this is where the waterline is and what happens when somebody is in it: the splash on arriving off the slide, a stride's rhythm of particles while wading, and the **slowdown and wet footsteps**, which it takes on entering and gives back on leaving (`FirstPersonController.SpeedScale` / `Wading`, written on the transition only, and restored in `OnDisable` for the one path — a cycle unloading with the player still in the water — that `Update` would never see). **Polled, never `OnTriggerEnter`** — the slide moves the player with `Teleport`, which switches the controller's collider off for the write, so the one frame this component exists to catch is a frame a trigger cannot see. It owns no geometry: the surface is a mesh with the water shader on it and the balls are `FloatingBalls`'. Nothing about it is solid, and a collider here would be what the slide's build-time ride raycast hits — the rider would be set down on the waterline instead of the floor.
- `Room/FloatingBalls.cs` — everything floating on room2-5's pool: 210 plastic balls, three rubber ducks and two beach balls. They are real **rigidbodies** — play asked for them to bump into each other, which a position written from a sine of the clock cannot do — and this component adds to the physics rather than replacing it: **buoyancy** as a damped spring to the height each was placed at (gravity is off, so nothing sinks and nothing can be knocked out of the pool), a weak **mooring** back toward that place (or a room walked through for fifteen minutes ends with everything in one corner), and **bob and drift** that are off for the balls — which is what lets a settled ball sleep, so 210 of them cost nothing until something disturbs them. On the **balloon layer**, because that layer already means "a light thing the player wades through and shoves aside": the controller excludes it and `pushLayers` already contains it. Allowed physics at all because nothing here is carried, recorded, socketed or reset — the same exception the tap's spray takes against CLAUDE.md §4.
- `Room/SymbolSlot.cs` — one recess in that room's wall: range, the **E** press, the prompt and the plate's light. `ChessPlacer` is to `ChessBoard` what this is to `CubeRoom`. The plate's light and the prompt used to be two different tests on purpose — `hand.Has` for a beacon readable across the room, `hand.Holding` for the press — and one object at a time collapsed them into one.
- `Room/FinalSlot.cs` — one shaped recess in Room4's console, operated with **E** while the object is in hand (`KeyLock`'s idiom: a socket is a fixture you stand at, where the board is a surface you aim at). Registers as an `IItemSocket` under its own name. **The "one socket per itemId" that once made that impossible is gone** (2026-08-15): `ItemRegistry` holds a LIST per id and a surrender records which one it was given to, because room2-2 has two stands that will take the same bucket and "the socket for Bucket" is not a question with an answer. The old worry — a fixture past the end of the run arbitrating what ghosts carry inside it — is answered by the name rather than by staying out of the registry. `AllFilled` refuses an empty array, like `FloorButton.AllActive`, and skips slots that name no object. **A FAMILY, added 2026-08-20 for room2-0** (`offerItemIds`): a recess can entertain a press for a whole set of objects while accepting exactly one of them. Empty — every recess built before room2-0 — means the two are the same question and this reads as it always did. Its four pedestals all want a billiard ball and each wants a different one, so without it the rim lighting up *was* the answer. A wrong ball is **refused with a red flash** and the press is claimed, which is `KeyLock`'s answer to a wrong key and the narrow case CLAUDE.md §1.2 allows: "only when it acts" is about presses the fixture was never offered, and `WantsInteractHint` has just said this one was. Refusing rather than keeping is a **ghost** decision — a wrong ball that stayed would be re-delivered by that iteration's past self forever.
- `Room/FinalRoomSequence.cs` — Room4 and the console in it. Raises the console when the player reaches the room, watches its three recesses, and sets `Completed` when all three escape objects are in — **the game's only exit condition**, and the only thing that breaks `LoopManager`'s `while(true)`. Then seals the door back to Room3, announces the break, turns every wall panel into a test card showing `ERROR` and shakes the building, before handing to `EndingSequence`. The clock runs through this room, so the console is a `RewardPlinth` (derived state) rather than a coroutine — an iteration can end in here. **The player keeps control until the scrim.** See `loop-and-ui.md`. **Cycle 2 has one too, since 2026-08-20** — room2-0, four pedestals on ONE `RewardPlinth` (the mover is a holder above all four, which is also what `MovesDuringPlay` finds by walking up). `opensWayOutOnBreak` is new with it: cycle 1's hatch is opened by `LoopManager.CrossToNextCycle` after the storey below has been woken, and cycle 2 has nothing to wake, so its break opens its own floor. That flag goes back to false the day cycle 3 exists.
- `Interactables/DoorIndicator.cs` — the lamp: one block split red/green, only ever one lit (albedo *and* emission — albedo alone looks like coloured plastic). **It tracks the condition, not the door.**
- `Room/ChessBoard.cs` — Room2West. Owns the grid (measured off the opening position, not divided out of the slab), which piece belongs on which square, and **one `IItemSocket` per piece** — which is the whole of how a ghost tidies the room without `GhostReplayer` knowing what a board is. A piece's socket is an empty object holding the pose that piece had before it was scattered, so `InsertInto`'s local identity reproduces the model's own arrangement. Also drives the room's ceiling lights, which are the reward.
- `Room/ChessReward.cs` — what Room2West does once its board is finished: the lights come up from **zero**, the board opens, the plinth rises. Split from `ChessBoard` on CLAUDE.md §2's boundary — that class owns the puzzle's rule, this one owns the room's theatre, the same way `FinalRoomSequence` is split from the button that starts it. Driven by a **float, not a coroutine**, so the loop's reset is total and instant. The ceiling panels are dimmed through a **MaterialPropertyBlock**, because `CeilingFixture` is one material shared by every room in the building and dimming it would black out Room1.
- `Interactables/ChessPlacer.cs` — the left button and the aim, and nothing else: it raycasts the board's collider alone (a hit test against everything would place a piece somewhere the player was not aiming, silently) and asks `ChessBoard` every question about *where*. Refuses **before** `PlayerHand.Surrender`, never after — a recorded surrender that could not be completed is a past self doing something the player did not.
- `Interactables/BalloonTool.cs` — uses an **overlap sphere, not a raycast**: in a room packed with balloons, having to line one up in the crosshair turns a physical act into a shooting gallery.
- `Loop/IterationLabel.cs` — the eyelids are built first in `BuildUI` so they sit at the back of the canvas and the label draws on top of the black rather than under it.
